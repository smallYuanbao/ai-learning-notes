## 题25：词嵌入 Word Embedding 的定义及常见方法

**我的回答**：

**定义**：把「词」这个离散符号，映射成「连续空间里的一个向量」。本质是把词之间的语义关系「编码」进向量空间——「苹果」和「香蕉」的向量距离近（都是水果），和「汽车」的距离远。

**经典例子**：`国王 - 男人 + 女人 ≈ 王后`，向量能做加减法表达语义关系。

**常见方法**（按演进顺序）：

| 方法 | 特点 |
|:---|:---|
| **Word2Vec** | 经典鼻祖，静态词向量，一词一义 |
| **GloVe** | 基于全局共现统计，也是静态 |
| **FastText** | 引入子词，能处理罕见词/形态变化 |
| **BERT 系** | 动态词向量，随上下文变化，一词多义 |

> **前端类比**：one-hot 是每个词一个独立维度、词与词互不相干；embedding 是稠密向量、向量距离表达语义——就像把「用户 ID」映射成「用户画像向量」后能算「像不像」。

**项目关联**：bge-m3 就是 BERT 系 embedding，我项目里的语义检索底层就是词嵌入的「句级」扩展。

**关键词**：词嵌入、Word Embedding、one-hot、稠密向量、语义关系、Word2Vec、GloVe、FastText、BERT

## 题2：Word Embedding 在文本分类任务中的应用方法

**我的回答**：

词嵌入在文本分类里是「特征工程」——把离散的文本变成模型能算的连续向量，再喂给分类器。

**流程**：

```
文本 → 分词 → 每个词查 embedding 表 → 得到向量序列
     → 池化（平均 / 取 CLS 向量）→ 得到句向量 → 分类器（softmax）
```

**为什么用 embedding 而不是 one-hot**：one-hot 是稀疏高维向量，词与词毫无关系（「苹果」和「香蕉」的 one-hot 距离一样远）；embedding 是稠密低维，相似词向量接近，模型更容易学到「语义相近的文本类别也相近」，分类准确率更高、还降维。

> 现代做法：直接用 BERT 把整句话编码成一个向量（CLS）接分类头，替代「分词 + 平均池化」的老流程。

**项目关联**：我项目里文本「意图路由」本质就是分类任务，用 embedding 表示语义。

**关键词**：Word Embedding、文本分类、特征工程、池化、CLS、softmax、one-hot、降维

## 题5：文本相似度的比较方法

**我的回答**：

文本相似度就是「两个向量怎么比像不像」，是 RAG 检索的直接核心：

| 方法 | 含义 | 特点 |
|:---|:---|:---|
| **余弦相似度** | 看两个向量的「夹角」 | 只看方向、不看长度，最常用 |
| **点积** | 逐维相乘再求和 | 同时受方向 + 长度影响 |
| **欧氏距离** | 看两个点的直线距离 | 受长度影响大 |

**为什么余弦最常用**：文本长度差异大，向量长度往往不反映语义（「苹果」一句话和一段话讲苹果，语义近但向量长度差很多），余弦只看方向，能正确判断「都指向苹果语义」。

> RAG 里就是「query 向量 vs 文档向量算余弦相似度，取 Top-K」。

**项目关联**：baby-ai 检索时 query 与文档 chunk 就是算余弦相似度排序取 Top-K。

**关键词**：文本相似度、余弦相似度、点积、欧氏距离、向量夹角、Top-K 检索

## 题8：注意力机制的定义及对 NLP 模型性能的改善作用

**我的回答**：

**定义**：让模型在理解/生成时，**关注输入里「最相关」的部分**，给不同位置不同权重，而不是一视同仁。

**QKV 三件套**：

```
Query（我要找什么）· Key（每个位置有什么）→ 算相似度 → 归一化成权重 → 对 Value 加权求和
```

一句话：**「谁跟我最相关，我就多听谁的」**。

**改善作用**（对比 RNN/LSTM）：

1. **解决长距离依赖**：RNN 要按顺序逐个读，读到后面忘了前面；注意力一步就能看到所有位置，直接「跳到」最相关处。
2. **可并行计算**：RNN 串行、慢；注意力各位置并行算，训练/推理都快。

> **对 RAG 的意义**：我的 rerank 模型（bge-reranker）本质就是基于 attention 的交叉编码器——把 query 和文档拼一起，用 attention 算「逐字细粒度相关度」。所以 attention 是我 rerank 的底层原理。

> **前端类比**：注意力 ≈ 「搜索高亮」——跟搜索词相关的地方被高亮优先看，其余略过。

**项目关联**：bge-reranker（基于 attention）已在项目中用于精排。

**关键词**：注意力机制、Attention、QKV、Query、Key、Value、权重、长距离依赖、并行、rerank、交叉编码器

## 题10：BERT 的优化、微调及在特定 NLP 任务中的应用

**我的回答**：

BERT 的核心范式是**「预训练 + 微调」**——一次预训练，到处复用：

| 阶段 | 做什么 |
|:---|:---|
| **预训练** | 在海量无标注语料上，用 MLM（掩码语言模型）+ NSP 训练出通用语言表示 |
| **微调** | 在特定任务上，加一个「任务头」，用少量标注数据继续训练，全模型参数（或部分）更新 |

**微调怎么落地**：拿预训练好的 BERT → 在句子/文档前加 `[CLS]` → 顶层加一个分类层 → 用任务数据（如情感标注）训练几轮 → 得到专用模型。

**典型应用**：文本分类、情感分析、命名实体识别（NER）、问答（QA）、句向量 embedding。

> **注意**：我项目里没走「微调 BERT」这条重路线，而是直接用预训练好的 bge-m3 做 embedding + bge-reranker 做重排——属于「用现成能力」而非「微调定制」。

**项目关联**：bge-m3（BERT 系预训练模型）直接用于 embedding，未做微调。

**关键词**：BERT、预训练、微调、MLM、NSP、CLS、任务头、文本分类、NER、情感分析

## 题11：CBOW 与 Skip-gram 的适用场景差异

**我的回答**：

两者都是 Word2Vec 的两种训练方式，核心思想一致——「不靠人工标注，靠上下文猜词，训练副产品就是词向量」。区别在于**预测方向相反**：

| 方法 | 方向 | 特点 |
|:---|:---|:---|
| **CBOW** | 用「上下文」预测中心词（周围猜中间） | 快，适合大数据集、高频词 |
| **Skip-gram** | 用「中心词」预测上下文（中间猜周围） | 慢，但对低频词效果更好 |

> 记忆口诀：**CBOW 用周围猜中间，Skip-gram 用中间猜周围**。

**适用场景**：

- **CBOW**：语料大、追求训练速度，词频分布均匀时用。
- **Skip-gram**：语料小、或在意低频词/生僻词质量时用（它每个词当中心词训多次，低频词被「练」得更充分）。

**项目关联**：这两个都是「怎么练出静态词向量」，我项目用 BERT 系动态向量，知道概念即可。

**关键词**：CBOW、Skip-gram、Word2Vec、上下文预测、中心词、低频词、训练速度

## 题13：Word2Vec 词向量的获取方法及评估方式

**我的回答**：

**获取方法**：无监督训练——不用人工标注，让模型做「完形填空」式预测（用上下文猜中心词 / 用中心词猜上下文），**训练副产品就是词向量**。核心是「分布式假设」：一个词的含义由它周围出现的词决定。

**评估方式**（两类）：

| 类型 | 做法 | 例子 |
|:---|:---|:---|
| **内在评估** | 直接测向量本身的语义质量 | 词类比（king - man + woman ≈ queen）、相似词召回 |
| **外在评估** | 看词向量喂给下游任务的效果 | 文本分类/情感分析准确率 |

> 内在评估快但可能和真实任务脱节，外在评估准但慢——面试知道这两种思路即可。

**项目关联**：静态词向量的获取/评估是 BERT 动态 embedding 的前身，理解「向量怎么来的、怎么衡量好坏」。

**关键词**：Word2Vec、无监督训练、分布式假设、词类比、内在评估、外在评估、词向量

## 题15：Word2Vec 到 BERT 的技术改进

**我的回答**：

这是 NLP 最常被问的「演进」问题，一句话：**Word2Vec 是静态词向量，BERT 是动态词向量**。

| 维度 | Word2Vec | BERT |
|:---|:---|:---|
| 向量性质 | **静态**，一词一向量 | **动态**，随上下文变化 |
| 上下文 | 不感知上下文 | 强感知上下文（双向） |
| 一词多义 | 分不开 | 分得开 |

**例子**：「苹果」在「吃苹果」和「苹果手机」里——

- Word2Vec 给**同一个**向量（水果和手机混在一起）；
- BERT 给**不同**向量（两个「苹果」向量不同）。

> **这就是为什么 RAG/语义检索用 BERT 系 embedding 而不是 Word2Vec**——检索需要「理解上下文里的真实含义」，静态向量做不到。

**项目关联**：bge-m3 是 BERT 系动态 embedding，正是选型时「放弃 Word2Vec 静态向量」的原因。

**关键词**：Word2Vec、BERT、静态词向量、动态词向量、一词多义、上下文、双向

## 题16：BERT 模型的架构及应用场景

**我的回答**：

BERT（2018，Google）是**双向 Transformer 编码器**，几乎所有现代 embedding 模型的架构基础。

**两个核心特点**：

| 特点 | 含义 | 对比 |
|:---|:---|:---|
| **双向** | 看「左右两边」上下文理解一个词 | GPT 单向只看左边 |
| **预训练 + 微调** | 先海量语料预训练，再下游任务微调 | 一次预训练到处复用 |

**怎么做到双向**：MLM（掩码语言模型）——随机盖住句子里的词，让模型根据**左右上下文**预测被盖住的词，逼它同时用两边信息。

**应用场景**：

- 直接产出句向量（`[CLS]`）做 embedding / 检索。
- 加分类头做文本分类、情感分析、NER。
- 作为下游任务的基础模型微调。

**项目关联**：bge-m3、bge-reranker 都是 BERT 系架构，我项目的 embedding 和重排直接受益于 BERT。

**关键词**：BERT、双向 Transformer、编码器、MLM、预训练、微调、CLS、embedding、NER

## 题17：BERT 与 CBOW 的 mask 方式差异

**我的回答**：

两者都是「预测被遮住的词」，但 mask 的**范围、粒度、上下文视野**完全不同：

| 维度 | CBOW | BERT（MLM） |
|:---|:---|:---|
| 遮什么 | 只「遮」中心词（1 个），用周围窗口词猜它 | 随机 mask 句子中 **15%** 的词，任意位置 |
| 上下文视野 | **局部窗口**（固定几个词） | **全局双向**（整句左右两边） |
| 向量性质 | 静态平均 | 动态（Transformer 双向编码） |
| mask 细节 | 无专门 mask token | 80% 换 [MASK] + 10% 换随机词 + 10% 保留原词 |

**关键差异**：CBOW 的「上下文」是中心词前后固定几个词的**局部窗口**，词向量是上下文词的简单平均（静态）；BERT 是随机遮任意位置的词、用整句的**全局双向**上下文预测，产出随上下文变化的动态向量。

> BERT 的「10% 换随机词」是为了防止模型只学 [MASK] 符号、不学真实上下文。

**项目关联**：知道 BERT 的 mask 机制，能解释为什么 BERT 是双向的、动态的（见题15/16）。

**关键词**：CBOW、BERT、MLM、mask、局部窗口、全局双向、15%、[MASK]、静态向量、动态向量

## 题20：BERT 对文本中罕见词的处理方法

**我的回答**：

BERT 用 **subword（子词）分词**解决罕见词/未知词问题——把罕见词拆成更小的、常见的子词单元。

**例子**：「unhappiness」→ 拆成 `un + happiness`；「unhappy」→ `un + happy`。这样「un」这个前缀能被「unhappy / unknown / unfair」等词共享，罕见词不再是「没见过的完整词」，而是「见过子词的组合」。

**为什么重要**：

- 传统分词对词典外（OOV）的词只能标「未知词」，信息丢失。
- subword 让没见过的新词也能用子词拼出来，模型仍能编码其含义。

> WordPiece 是 BERT 用的 subword 算法（Google 提出）。

**项目关联**：bge-m3 同样用 subword 分词，所以我项目检索时遇到生僻词/新词不会直接失效。

**关键词**：subword、子词分词、WordPiece、罕见词、OOV、未知词、BERT

## 题28：BERT 输入长度限制的解决方法

**我的回答**：

BERT 的输入长度通常限制在 **512 token**（自注意力复杂度 O(n²) + 位置编码限制），超长文本的常见解法：

| 方法 | 做法 | 特点 |
|:---|:---|:---|
| **截断** | 只取前 512 token | 简单但丢尾部信息 |
| **分块/滑动窗口** | 长文档切成多段分别编码，再合并（取平均/拼接/CLS 池化） | 保留全篇，但段间无交互 |
| **层级编码** | 先分句/段各自编码，再聚合到上层 | 兼顾全局 |
| **换长上下文模型** | Longformer、BigBird 用稀疏注意力把长度扩到几千 | 突破 512，代价是复杂度 |

> **RAG 语境下更务实**：与其硬塞超长文档进 embedding 模型，不如「切块存库、检索时只编码最相关的 Top-K 块」——这正好是我项目的做法。

**项目关联**：bge-m3 支持长上下文，但我项目仍按「切块 + 检索」处理长文档，而非单条全编码。

**关键词**：BERT、512 token、输入长度限制、截断、分块、滑动窗口、层级编码、稀疏注意力、Longformer、BigBird
