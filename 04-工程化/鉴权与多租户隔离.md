# 鉴权与多租户隔离

> 📅 学习日期：2026-08-20
> 🔗 关联面试题：工程落地 4.14（多维度权限控制 + 越权规避）、2.13（用户身份安全传递）、Agent 专题题37（工具权限）
> 🎯 前置：本篇讲「应用层」的权限三件套——认证、授权、多租户隔离。和「Agent 工具权限」（沙箱/审批）是两码事，别混。

---

## 1. 三个概念，面试最容易被追问「区别」

权限体系里三个词经常一起出现，但边界完全不同：

| 概念 | 英文 | 回答的问题 | 手段 | baby-ai 例子 |
|:---|:---|:---|:---|:---|
| **认证** | Authentication | 你是谁？ | API Key / JWT / 密码 | 请求带 `Authorization: Bearer <key>`，服务端查 key→user_id |
| **授权** | Authorization | 你能干什么？ | RBAC（角色-权限表） | 普通用户只能看育儿内容，管理员能看成本报表 |
| **多租户隔离** | Tenancy | 你只能看自己的 | 数据加 owner 字段 + 查询过滤 | 宝宝档案表加 `user_id` 列，所有 SQL 带 `WHERE user_id=?` |

> 一句话记：**认证是「验明正身」，授权是「给权限」，隔离是「各看各的」**。三者是递进关系——先认出你是谁（认证），再决定你能干嘛（授权），最后保证你只能碰自己的数据（隔离）。

> **前端视角**：认证 ≈ 登录拿 token；授权 ≈ 前端的「菜单/按钮按角色显隐」；隔离 ≈ 多租户 SaaS（比如你用的 Notion，你只能看到自己团队的空间，看不到别人的）。前端最容易踩的坑是把「按钮隐藏」当成「安全」，其实只是体验优化——真正的安全永远在服务端。

## 2. API Key vs JWT（认证的两种主流手段）

| | API Key | JWT |
|---|---|---|
| 本质 | 「key → user_id」的映射表 | 无状态签名令牌 |
| 服务端状态 | **需要存映射**（dict / DB / Redis） | 无状态，靠签名校验，不存 |
| 能否携带信息 | 不能，key 就是个无意义字符串 | 能，payload 里塞 user_id、角色、过期时间 |
| 多实例 | 要共享映射（放 Redis/DB） | 天然无状态，多实例友好 |
| 适用 | 服务间调用、demo、内部系统 | 需要签发/刷新的用户体系 |
| 演进成本 | 低，先跑通隔离 | 高，要管签发/刷新/过期/注销 |

> 关键区别：**API Key 是「有状态」的（服务端要查表），JWT 是「无状态」的（验签即可）**。方案 A 用 API Key（进程内 dict 存映射），单实例 demo 够用；面试讲方案 B 就升到 JWT 或 Redis。

---

## 3. 多租户隔离的三种模式（数据怎么「各看各的」）

| 模式 | 做法 | 隔离性 | 成本 | 适用 |
|:---|:---|:---|:---|:---|
| **独立库** | 每个租户一个数据库 | 最强（物理隔离） | 最高 | 银行、政企，租户少且要求高 |
| **共享库 + tenant_id 列** | 一张表，每行带 `tenant_id` | 中（逻辑隔离） | 中 | 大多数 SaaS |
| **共享库 + 行级 owner** | 每行带 `user_id`，查询带过滤 | 中 | 低 | 方案 A、B2C 应用 |

> 方案 A 用的是**第三种**（行级 owner）：`children` 表加 `user_id` 列，每个 SQL 都 `WHERE user_id = ?`。这是 B2C 应用最常见的做法，成本最低、够用。

> **前端视角**：独立库 ≈ 每个客户一套独立部署；tenant_id 列 ≈ 一张表里用 `org_id` 字段区分公司；行级 owner ≈ 表里用 `user_id` 区分个人。三种都是「把『谁的』这个维度塞进数据里，查询时过滤」。

## 4. IDOR 越权（核心考点，必背）

**IDOR**（Insecure Direct Object Reference，不安全的直接对象引用）：攻击者通过**猜/改 URL 里的资源 ID**，直接访问不属于自己的对象。

```
GET /api/growth/children/c_b72800b6
```

如果服务端只校验「登录了没」，不校验「这个 child 是不是你的」，攻击者遍历 `c_xxx` 就能把别人家宝宝档案全拉出来。

**最经典的误区**：前端把别人的数据「藏起来」（不渲染、不加按钮），就以为安全了。**错**——攻击者不用你的前端，直接用 curl 改 ID 就能拿到数据。真正的隔离必须在**服务端每个查询都加 user_id 过滤**：

```python
# ❌ 只校验存在性，不校验归属 → IDOR 漏洞
"SELECT * FROM children WHERE child_id = ?"

# ✅ 同时校验归属 → 越权被拦在 SQL 层
"SELECT * FROM children WHERE child_id = ? AND user_id = ?"
```

> 一句话：**「前端不显示」是体验，「服务端不返回」才是安全。** 隔离边界永远在服务端，且要落到**每一处数据访问**（DB 查询、向量检索、缓存 key），漏一处就前功尽弃。

## 5. 项目关联（baby-ai 方案 A 实测）

方案 A 用「API Key 认证 + 行级 owner 隔离」打通了三个数据面，联调全部验证通过：

| 数据面 | 隔离实现 | 越权验证结果 |
|:---|:---|:---|
| 宝宝档案（SQLite） | `children` 表加 `user_id` 列 + 所有 SQL `WHERE user_id=?`；records 用 JOIN/子查询校验归属 | bob 直接 GET alice 的 childId → **404** |
| 上传文件（ChromaDB） | 每个 chunk 的 metadata 写 `user_id`，检索用 `$and` 双重过滤 `file_id + user_id` | bob 拿 alice 的 file_id 检索 → **0 命中** |
| 会话（内存） | 会话 key 从 `session_id` 改成 `user_id:session_id` | 同一 session_id 下两用户各自独立 |

**关键实现细节（面试可展开）：**

1. **认证**：`app/core/auth.py` 里 `API_KEYS = {"dev-key-alice": "user_alice", ...}`，`get_current_user_id` 从 `Authorization: Bearer <key>` 解析出 user_id，非法 key 返回 401。

2. **SQLite 迁移**：`CREATE TABLE IF NOT EXISTS` 不会给已存在的表加列，所以单独写了 `ALTER TABLE children ADD COLUMN user_id ...` 的幂等迁移，存量数据归到 `user_anonymous`。

3. **ChromaDB 双重过滤的坑**：多条件过滤不能直接并列 `{"file_id":…, "user_id":…}`，必须用 `{"$and":[…]}`——这是我联调时真实踩的坑，单测覆盖不到。

4. **为什么 API Key 放 Header 不放 query**：放 query 会被记进访问日志、浏览器历史，等于明文泄露；放 `Authorization` 头走 HTTPS 不落日志。

**范围裁剪**：方案 A 只隔离了三个核心数据面，play 模块（谜语）和 agent 端点暂未接鉴权——这是有意的「渐进式隔离」，面试可讲「先护住核心数据，再逐模块铺开」。

## 6. 面试怎么讲

> "权限我分三层看：**认证**验明身份（API Key / JWT），**授权**给能力（RBAC），**多租户隔离**保证各看各的（数据加 owner 字段）。我在 baby-ai 用 API Key 做认证，数据侧用「行级 owner」——`children` 表加 `user_id` 列，每个 SQL 都 `WHERE user_id=?`，上传文件在 ChromaDB metadata 里也写 user_id，检索用 `$and` 双重过滤。核心防线是**防 IDOR 越权**：不能只靠前端藏数据，必须在服务端每个查询都做归属校验。面试追问「API Key 和 JWT 区别」，我说 API Key 是有状态的 key→user 映射，JWT 是无状态签名令牌，多实例场景 JWT 更省事。"
