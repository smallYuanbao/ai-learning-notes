# RAG vs 微调——选型决策

> 📅 学习日期：2026-08-13
> 🔗 关联面试题：微调专题 题15、RAG 专题 题46

> 你已经懂了 RAG 是什么、微调是什么。这篇笔记解决一个更实际的问题：**站在老板面前，30 秒内告诉他该用哪个。**


## 1. 一个让你当场卡壳的决策场景

### 1.1 场景还原

你在公司里负责 AI 落地。有一天，产品经理跑过来问你：

> **「我们想做一个智能客服，能回答产品文档里的问题。你说，用 RAG 还是微调？」**

你脑子里的第一反应可能是：

- 我知道 RAG 是什么——外挂知识库，让模型临时查资料
- 我知道微调是什么——改模型权重，让它内化某种行为
- 但……**这俩到底该怎么选？**

你开始犹豫：

- 用 RAG？但有些场景 RAG 检索不准，回答质量不稳定
- 用微调？但微调成本高，而且产品文档天天更新，微调一次就得重训一次
- 要不……两个都用？

**你卡住了。而产品经理还在等你的答案。**

### 1.2 这个场景的本质

先别急着选。我们先想清楚：**你卡住的原因是什么？**

不是你不懂 RAG 或微调——你两个都懂。你卡住是因为：

> **你缺的不是「知识」，是「决策依据」。**

你知道这两个工具各自能干什么，但你不知道**在什么条件下该用哪个**。

这就像你手里有锤子和螺丝刀，你知道锤子能敲钉子、螺丝刀能拧螺丝，但面对一个「要固定两块木板」的需求，你还是得先判断：**这里该用钉子还是螺丝？**

### 1.3 这篇笔记要给你什么

读完这篇笔记，你至少要能拿到两个东西：

| 要拿到 | 用途 |
|:---|:---|
| **一句话判断口诀** | 30 秒内回答老板，覆盖 80% 的场景 |
| **一张决策树** | 面对复杂场景，照着流程走一遍就能出结论 |

### 1.4 先给你剧透答案

在展开细节之前，先给你那个「30 秒能回答」的口诀，让你心里有底：

> **模型「不知道」某件事 → 用 RAG（挂知识库，随时查）**
>
> **模型「知道」但「做得不对」→ 用微调（改权重，改行为）**

这两句话能解决大部分场景。但为什么？什么算「不知道」？什么算「做得不对」？边界在哪？

接下来的部分，我们一层层拆开。下一部分，先从「两者的本质区别」讲起——但这个区别，不是你在微调笔记里看过的静态对比，而是**站在「决策」的角度重新看一遍**。


## 2. 先分清——它们在解决不同性质的问题

### 2.1 别再背那张对比表了

你在微调笔记 §1.5 里已经见过一张「RAG vs 微调」的对比表：

| 方案 | 怎么做 | 适用场景 |
|:---|:---|:---|
| RAG | 外挂知识库，临时查资料 | 需要大量动态知识 |
| 微调 | 改模型权重，改变默认行为 | 需要稳定风格、固定格式 |

这张表是对的，但它有一个问题：**它讲的是「是什么」，不是「怎么选」。**

你背下这张表，面对「智能客服」需求时依然会卡壳——因为「动态知识」和「稳定风格」这两个词，在真实需求里是混在一起的。

> 产品经理不会说「我要动态知识」，他会说「我要一个能回答产品文档问题的客服」。你要做的，是从这句大白话里，拆出它到底属于哪一类问题。

### 2.2 两者解决问题的「性质」不同

RAG 和微调，解决的是**两种完全不同性质的问题**。这不是程度差别，是类别差别：

| 维度 | RAG 解决的问题 | 微调解决的问题 |
|:---|:---|:---|
| **问题性质** | 信息不足 | 行为不对 |
| **一句话** | 模型「不知道」这件事 | 模型「知道」但「做得不对」 |
| **知识从哪来** | 外部（知识库，随时可换） | 内部（权重，训练时固化） |
| **改的是什么** | 不改模型，改「喂给模型的东西」 | 改模型，让「模型自己」变 |
| **类比** | 给员工一本随时更新的手册 | 培训员工，让他自己就会 |

> **关键洞察**：RAG 是「外挂」，微调是「内化」。一个改输入，一个改模型。

### 2.3 用一个例子彻底分清

还是那个「审核合同」的需求（微调笔记里用过）。我们假设你手里有一个通用大模型，它已经「认识」合同是什么。

**场景 A：模型不知道「你公司的合同模板长什么样」**

- 你问模型：「帮我校验这份合同是否符合我们公司的标准格式」
- 模型懵了：「我不知道你们公司的标准格式是什么」
- 这是**信息不足** → 该用 RAG，把你公司的合同模板挂进知识库

**场景 B：模型知道格式，但每次输出都不稳定**

- 你已经把模板给了模型（不管是通过 Prompt 还是 RAG）
- 但模型有时候输出「甲方、乙方」的格式，有时候输出「第一部分、第二部分」的格式
- 内容都对，但**格式飘忽不定**
- 这是**行为不对** → 该用微调，让模型「内化」这套格式

> **一句话总结**：RAG 解决「它不知道」，微调解决「它知道了却做不稳」。

### 2.4 边界情况：两者都沾一点怎么办？

真实需求往往不是纯 A 或纯 B。比如「智能客服」：

- 它需要「知道」产品文档的最新内容 → 这是**信息不足** → 偏 RAG
- 它又需要「用客服的口吻、固定的回复格式」→ 这是**行为不对** → 偏微调

这时候怎么办？先别急着做决定。这正是第三部分（决策树）要解决的问题。

> **先记住一个心法**：判断一个需求偏哪边，先问一句——「如果我把所有资料都塞给它，它就能做对吗？」

- 如果「塞资料」就够了 → 信息不足 → RAG
- 如果「塞了资料还是做不稳」→ 行为不对 → 微调（或两者组合）

这一问，能帮你过滤掉一半的纠结。

### 2.5 本部分小结

| 问题 | 答案 |
|:---|:---|
| RAG 和微调是程度差别吗？ | 不是，是**类别差别**——一个改输入，一个改模型 |
| 怎么快速判断？ | 问「塞够资料能不能解决」→ 能则 RAG，不能则微调 |
| 边界情况怎么办？ | 别急着选，进入第三部分的决策树 |

> 下一部分，我们把这个「心法」变成一张能照着走的**决策树**。


## 3. 决策树——照着走一遍就出结论

### 3.1 为什么需要一张决策树？

第 2 部分给了你一个「心法」，但心法是**启发式**的，遇到复杂需求还是会犹豫。

决策树的作用是：**把心法变成流程**，你不需要「悟」，只需要「照着走」。

> 类比：心法是「感觉今天会下雨就带伞」，决策树是「查天气预报 App」——前者靠直觉，后者靠步骤。

### 3.2 决策树（全文核心）

```
                    ┌─────────────────────────────┐
                    │  你的核心诉求是什么？        │
                    └──────────────┬──────────────┘
                                   │
              ┌────────────────────┼────────────────────┐
              │                    │                    │
              ▼                    ▼                    ▼
     ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
     │ 模型「不知道」 │      │ 模型「知道」 │      │  两者都要    │
     │ （信息不足）  │      │ 但「做不稳」 │      │（知识+行为） │
     └──────┬──────┘      └──────┬──────┘      └──────┬──────┘
            │                    │                    │
            ▼                    ▼                    ▼
     ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
     │  知识会频繁   │      │  有稳定标注   │      │   RAG +     │
     │  更新吗？    │      │  数据吗？    │      │  微调 组合   │
     └──┬───────┬──┘      └──┬───────┬──┘      └─────────────┘
        │       │            │       │
      会更新   不更新       有数据   没数据
        │       │            │       │
        ▼       ▼            ▼       ▼
   ┌────────┐ ┌────────┐ ┌────────┐ ┌──────────────┐
   │  RAG   │ │ RAG 或 │ │  微调  │ │ 先 RAG +     │
   │        │ │ 微调固化│ │        │ │ 精细 Prompt   │
   │ (主推) │ │ (二选一)│ │ (主推) │ │ (过渡方案)   │
   └────────┘ └────────┘ └────────┘ └──────────────┘
```

### 3.3 拆解每个分支

**分支 1：模型「不知道」→ 知识频繁更新 → RAG**

典型场景：产品文档问答、财报解读、新闻摘要、客服 FAQ。

为什么 RAG？因为知识天天变，微调一次就固化一次，重训成本高、响应慢。RAG 只要更新知识库，模型立刻能用新知识。

> **口诀**：知识是「流」的，用 RAG（外挂，随时换）；知识是「冻」的，才考虑微调。

**分支 2：模型「不知道」→ 知识基本不变 → RAG 或微调二选一**

典型场景：公司内部的固定规章制度、历史知识库。

这时候两者都可行，需要看**成本**和**稳定性**：如果追求省钱、快速上线，选 RAG；如果追求极致稳定（比如法律条款不能答错），可以考虑微调固化。

> 这个分支是「灰色地带」，往往需要结合第 4 部分的六个维度来定。

**分支 3：模型「知道」但「做不稳」→ 有标注数据 → 微调**

典型场景：固定格式输出（周报、合同、邮件）、特定风格迁移、稳定的推理路径。

为什么微调？因为问题是「行为不稳」，RAG 只是喂资料，改不了模型的「输出习惯」。必须微调让模型「内化」行为。

> **口诀**：内容是 RAG 的活，行为是微调的活。

**分支 4：模型「知道」但「做不稳」→ 没标注数据 → 先 RAG + 精细 Prompt**

典型场景：想要稳定风格，但还没有积累足够的「标准答案」数据。

这时候别急着微调（没数据微调不好），先用 RAG 兜底内容 + 精心设计的 Prompt 约束格式，同时开始积累标注数据，等数据够了再转微调。

> **这是一个「过渡态」**，不是终点。很多人卡在这，其实是把过渡态当成了最终方案。

**分支 5：两者都要 → RAG + 微调组合**

典型场景：智能客服（既要最新产品知识，又要固定客服口吻）。

这是最高级的用法，第 6 部分会单独展开。

### 3.4 决策树背后的「唯一原则」

你可能会问：这么多分支，背后有没有一个统一的判断标准？

有，就一条：

> **知识在变 → RAG 负责；行为要稳 → 微调负责。**

- 知识的「更新频率」决定要不要 RAG
- 行为的「稳定性要求」决定要不要微调
- 两个独立判断，最后组合

记住这一条，你甚至可以不用背决策树——现场推导出来。

### 3.5 本部分小结

| 问题 | 答案 |
|:---|:---|
| 决策树的核心判断点？ | ① 知识要不要更新 ② 行为要不要稳定 |
| 最常见的主推方案？ | 动态知识→RAG，稳定行为→微调 |
| 没数据想微调怎么办？ | 先 RAG + 精细 Prompt 过渡，攒数据 |
| 最高级用法？ | RAG + 微调 组合（知识用 RAG，行为用微调） |

> 下一部分，我们把「六个决策维度」展开——决策树告诉你「走哪条路」，六个维度告诉你「为什么走这条路」。


## 4. 六个决策维度——把「为什么」说清楚

### 4.1 从「走哪条路」到「为什么走这条路」

第 3 部分的决策树给你结论，但面试或汇报时，对方一定会追问一句：

> **「你为什么选 RAG？（为什么不是微调？）」**

这时候光说「因为知识会更新」是不够的——你要能**拆成维度**来说服人。

这六个维度，就是你的「论据库」。每个维度问一个问题，答案偏向哪边，就倾向选哪个。

### 4.2 六个维度一览

先看总表（后面逐个拆）：

| 维度 | 问自己 | 偏 RAG | 偏微调 |
|:---|:---|:---|:---|
| ① 数据量 | 有没有「标准答案」标注数据？ | 没有 / 很少 | 有（几百~几千条） |
| ② 更新频率 | 知识多久变一次？ | 天 / 周级别 | 月 / 年级别，基本不变 |
| ③ 成本 | 预算、时间、算力够吗？ | 省（不训练） | 贵（要训练） |
| ④ 可解释性 | 需要「给出来源」吗？ | 要（可引用文档） | 不需要 |
| ⑤ 稳定性 | 格式/风格必须严格一致吗？ | 不严格 | 严格 |
| ⑥ 上线速度 | 多久要上线？ | 几天内 | 有几周时间 |

### 4.3 逐个拆解

**维度 ① 数据量：你手里有「标准答案」吗？**

微调的前提是「有标注数据」——也就是一堆「输入 → 标准答案」的配对。

- 没有数据 → 微调无从谈起 → 只能 RAG（或先攒数据）
- 有几百~几千条稳定数据 → 微调开始有意义

> 这是一票否决维度：**没数据，其他维度再好也没法微调。**

**维度 ② 更新频率：知识是「流」还是「冻」？**

- 天天变（产品文档、新闻、行情）→ RAG，随改随用
- 基本不变（规章制度、历史库）→ 可以微调固化

> 微调的代价是「固化」：知识一变，就得重训。

**维度 ③ 成本：你的预算是多少？**

- RAG：搭向量库 + 检索，几乎不用训练，GPU 需求低
- 微调：LoRA 也要 4-8GB 显存 + 几小时~几天训练，还得维护数据集

> 省钱快速 → RAG；舍得投入换长期稳定 → 微调。

**维度 ④ 可解释性：要不要「给出来源」？**

- 需要引用原文（法律、医疗、客服合规）→ RAG 天然支持「答案 + 出处」
- 纯风格/格式，不需要溯源 → 微调无所谓

> 这一条 RAG 是「降维打击」——微调后的模型说不出「我是根据哪条文档答的」。

**维度 ⑤ 稳定性：格式/风格必须「每次都一样」吗？**

- 要求 100% 一致（合同、周报、API 输出格式）→ 微调，把行为固化进权重
- 差不多就行 → Prompt + RAG 也能凑合

> 微调解决的就是「做不稳」，正是这一维度的核心。

**维度 ⑥ 上线速度：你有多急？**

- 明天就要演示 → RAG，当天能搭起来
- 有几周打磨 → 微调来得及

> 时间压力常常是最终拍板的那根稻草。

### 4.4 怎么用这六个维度？

不用六个全背，实战里记住**优先级**即可：

1. 先看 **① 数据量**——没数据，直接 RAG，不用往下看
2. 再看 **② 更新频率** 和 **⑤ 稳定性**——这俩对应决策树的两个主分支
3. 剩下的 **③④⑥** 是「加分项」，用来在都可行时做最终取舍

### 4.5 本部分小结

| 问题 | 答案 |
|:---|:---|
| 六个维度分别管什么？ | 数据 / 频率 / 成本 / 可解释性 / 稳定性 / 速度 |
| 哪个是一票否决？ | ① 数据量（没数据没法微调） |
| 哪个最容易被忽略？ | ④ 可解释性（RAG 能引来源，微调不能） |
| 实战优先级？ | 数据量 → 频率/稳定性 → 成本/可解释性/速度 |

> 下一部分，我们拆掉三个最常见的误区——「微调一定比 RAG 高级」「RAG 不用微调」「两个都用最保险」。


## 5. 三个常见误区——别被这些说法带偏

### 5.1 误区一：「微调一定比 RAG 高级」

很多人觉得微调是「内功」，RAG 是「外挂」，所以微调更高级、更厉害。

**真相**：两者是不同性质的工具，没有高低之分。

- 需要最新知识 → RAG 吊打微调（微调后的知识是「过期快照」）
- 需要稳定行为 → 微调吊打 RAG（RAG 改不了输出习惯）

> 选型不是「选更高级的」，是「选对症的」。用错工具，再「高级」也没用。

### 5.2 误区二：「用了 RAG 就不用微调」（反之亦然）

**真相**：两者不互斥，反而经常组合。

- RAG 解决「知识」，微调解决「行为」，各管一摊
- 很多生产级系统是「微调过的模型 + RAG 知识库」

> 不要陷入「二选一」的思维陷阱。真实系统往往是「都用，但分工不同」。

### 5.3 误区三：「两个都用最保险」

**真相**：组合使用不是免费的，有额外成本。

- 微调要数据 + 算力 + 时间
- RAG 要建库 + 调检索 + 维护
- 两个都上 = 两倍维护成本，如果需求只需要一个，纯属浪费

> 「组合」是手段不是目的。只有当需求**确实同时需要**「最新知识 + 稳定行为」时，才值得组合。

### 5.4 本部分小结

| 误区 | 真相 |
|:---|:---|
| 微调比 RAG 高级 | 没有高低，只有对症 |
| 用了 RAG 就不用微调 | 两者常组合，各管一摊 |
| 两个都用最保险 | 组合有成本，按需才上 |

> 下一部分，专门讲「组合使用」的正确姿势——什么时候组合、怎么分工、有没有坑。


## 6. 组合使用——RAG + 微调的正确姿势

### 6.1 什么时候需要组合？

组合不是默认选项，只有当需求**同时满足两个条件**才值得：

1. **知识要最新**（信息不足 → 需要 RAG）
2. **行为要稳定**（做不稳 → 需要微调）

典型场景：**智能客服**——既要回答最新产品文档（RAG），又要固定客服口吻和回复格式（微调）。

### 6.2 组合的分工

| 模块 | 负责什么 | 用什么 |
|:---|:---|:---|
| 知识 | 「答案是什么」 | RAG（检索最新文档） |
| 行为 | 「怎么答」 | 微调（固化口吻、格式） |

一句话：**RAG 提供素材，微调决定表达。**

### 6.3 组合的两种搭法

**搭法 A：微调模型 + 挂 RAG（最常见）**

- 先用 LoRA 微调一个「懂你风格」的模型
- 再给它接上 RAG 知识库，让它「用你的风格 + 最新资料」作答

**搭法 B：先 RAG 后微调（渐进式）**

- 先纯 RAG 上线，跑一段时间
- 从真实对话里攒「好答案」数据
- 攒够了再微调，把「稳定行为」固化

> 搭法 B 尤其适合「一开始没数据」的情况——这正是决策树分支 4 的延续。

### 6.4 组合的坑

| 坑 | 说明 | 对策 |
|:---|:---|:---|
| 成本翻倍 | 两套系统都要维护 | 确认需求真的两个都需要 |
| 检索不准拖累微调 | RAG 检索错，再好的微调也答不对 | 先调好 RAG，再叠加微调 |
| 微调「洗掉」通用能力 | 过度微调可能灾难性遗忘 | 数据量适度，别刷太狠 |

### 6.5 本部分小结

| 问题 | 答案 |
|:---|:---|
| 组合的前提？ | 同时需要「最新知识」+「稳定行为」 |
| 怎么分工？ | RAG 供素材，微调定表达 |
| 没数据怎么起步？ | 先 RAG 上线攒数据，再微调（渐进式） |
| 最大坑？ | 检索不准，微调再好也白搭 |

> 下一部分（最后），我们用两个真实案例，把前面所有内容走一遍。


## 7. 案例走查——把整套方法跑一遍

### 7.1 案例一：智能客服

**需求**：回答产品文档问题，但要用客服口吻、固定格式回复。

**走决策树**：

1. 核心诉求？→ **两者都要**（要最新知识 + 要固定口吻）
2. 知识会频繁更新吗？→ **会**（产品天天发新版）
3. 有稳定标注数据吗？→ **一开始没有**

**结论**：

- 先上 **RAG**，接最新产品文档
- 同时用**精细 Prompt** 约束客服口吻
- 跑一段时间，从真实对话里**攒好答案**
- 数据够了，用 **LoRA 微调**固化口吻和格式
- 最终形态：**微调模型 + RAG** 组合

> 这是一个典型的「渐进式」路径：RAG → 攒数据 → 微调 → 组合。

### 7.2 案例二：合同审核助手

**需求**：帮法务审核合同，必须符合公司模板，且要能引用条款原文。

**走决策树**：

1. 核心诉求？→ **模型「不知道」**公司合同模板 → 偏信息不足
2. 知识会频繁更新吗？→ **基本不变**（模板固定）
3. 需要「给出来源」吗？→ **要**（法务要看到依据哪条）

**结论**：

- 用 **RAG**，把公司合同模板 + 历史判例挂进知识库
- 天然支持「答案 + 出处」，法务放心
- **不需要微调**——因为不需要改变输出风格，只要内容对、有来源即可

> 这个案例的亮点：**可解释性**（维度④）成了决定因素，一票把方案定成了 RAG。

### 7.3 两个案例对比

| 维度 | 智能客服 | 合同审核 |
|:---|:---|:---|
| 核心诉求 | 两者都要 | 信息不足 |
| 更新频率 | 频繁 | 基本不变 |
| 可解释性 | 不强求 | 必须 |
| 最终方案 | RAG → 微调 → 组合 | 纯 RAG |

```

              │ 问：塞够资料，它能做对吗？    │
              └──────────────┬───────────────┘
```

## 9. 面试怎么讲

> "RAG 和微调解决的是两类问题：RAG 解决信息不足（模型不知道），微调解决行为不对（模型知道了但做不稳）。一句话判断——塞够资料能不能解决？能就 RAG，不能就微调。

> 选型我走两个独立判断再组合：知识要不要更新（要更新→RAG），行为要不要稳定（要稳定→微调）。六个维度里，数据量是一票否决（没数据没法微调），可解释性最容易忽略（RAG 能引来源，微调不能）。

> 生产级系统往往是组合——RAG 提供素材，微调决定表达。我项目是先用 RAG 上线攒数据，再 LoRA 微调固化行为。"
