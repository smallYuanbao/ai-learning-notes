## 1. 为什么需要负载均衡（单机有天花板）

一台机器再强，也有硬上限：CPU 核数、内存大小、网络带宽、GPU 显存、文件描述符连接数……都有限。

高并发场景下，单机到极限了，只能「加机器」。但加机器就带来一个新问题：**请求来了，该发给哪一台？** 这就是负载均衡要解决的问题。

> **前端视角**：这跟「接口扛不住，就部署多台服务器，前面放个 CDN / Nginx 分流」一个道理。负载均衡就是那个「分流器」。

## 2. 两种扩展：纵向 vs 横向

| 方式 | 做法 | 优缺点 |
|:---|:---|:---|
| **纵向扩展（Scale Up）** | 换更强的机器（加 CPU/内存/换更大的 GPU） | 简单，但有天花板、越来越贵、单点风险 |
| **横向扩展（Scale Out）** | 加更多机器，多台一起扛 | 便宜、无限加、但要负载均衡 + 无状态 |

> **一句话**：高并发靠**横向扩展**。纵向到顶很快，横向才能无限堆机器。面试问「怎么扛住高并发」，答案最终都落到「横向扩展 + 负载均衡」。

## 3. 负载均衡的两个作用（别只说「分摊」）

1. **分摊压力**：把请求平均分到多台机器，别让某台累死、其他闲着。
2. **高可用**：一台机器挂了，负载均衡器通过**健康检查**发现它，把它剔除，流量自动切到健康的机器——用户无感知。

> 很多人以为负载均衡只是为了「快」，其实它的「高可用」作用同等重要——这是故障时服务不崩的保障。

## 4. 常见的负载均衡策略（面试必问）

一张表先快速过一眼，四个策略的核心区别是「**下一个请求发给谁**的判断依据不同」：

| 策略 | 判断依据 | 适用 |
|:---|:---|:---|
| **轮询（Round Robin）** | 轮流发 | 各机器性能相同、请求工作量差不多 |
| **加权轮询（Weighted RR）** | 按权重分 | 机器性能不均 |
| **最少连接数（Least Connections）** | 看谁最闲 | 请求耗时差异大（如 LLM） |
| **一致性哈希（Consistent Hashing）** | 按 key 固定落点 | 加/减机器时缓存失效最少 |

下面逐个拆开，带数字。

**① 轮询（Round Robin）——最简单，轮流发**

**机制**：维护一个计数器，每来一个请求发给「下一台」，发完最后一台回到第一台，循环往复。

**例子**（3 台机器 A/B/C）：

```
请求 1 → A
请求 2 → B
请求 3 → C
请求 4 → A
请求 5 → B
请求 6 → C
```

就像「发牌」——一人一张轮流发。

**它的问题**：只看「发了几次」，不看「这台是不是还在忙」。请求工作量都一样时它很公平；但如果 A 收到的都是 10 秒长任务、B 都是 1 秒快任务，A 会越积越多——**分配均匀 ≠ 负载均匀**。所以轮询只适合「所有请求工作量差不多」的场景。

**② 加权轮询（Weighted RR）——给强机器多分点**

**机制**：给每台机器一个「权重」，权重大的多分请求。

**例子**：A 是 8 核强机器（权重 3），B 是 4 核（权重 2），C 是 2 核（权重 1）。

```
每 6 个请求：A 拿 3 个、B 拿 2 个、C 拿 1 个
顺序大致：A → A → B → A → C → B
```

**适用**：机器性能不均——扩机器时新旧机器配置不一样，给强的多分、弱的分点。

> 前端类比：按能力派活，老员工多派、实习生少派。

**③ 最少连接数（Least Connections）——看谁现在最闲**

**机制**：看每台机器「当前正在处理的连接数」，谁最闲（连接数最少）就发给谁。

**例子**（LLM 场景，耗时差异大）：

```
此刻：A 在跑 5 个（每个 10 秒）、B 在跑 2 个、C 在跑 8 个
新请求 → 发给 B（它最闲）
```

**为什么需要它**：轮询只「轮流发」，A 被 5 个 10 秒长任务占满时，轮询可能还继续往 A 塞。最少连接数会「看一眼谁有空」再发——**这是 LLM 场景最常用的策略**，因为 LLM 请求耗时差异巨大（1 秒到 30 秒都有）。

> 前端类比：抢车位——不是轮流停每个区域，而是看哪片有空停哪片。

**④ 一致性哈希（Consistent Hashing）——解决「加机器后缓存全失效」**

这个最难，先讲它要解决的问题。

**问题背景**：3 台机器，用最简单的方法 `hash(用户id) % 3` 分配（余 0 去 A、余 1 去 B、余 2 去 C），同一个用户永远去同一台——好处是这台机器能缓存该用户的数据。

**但加机器就崩**：加一台变 `hash % 4`，几乎所有用户的余数都变了，原本去 A 的现在去 D……每台机器的缓存**全部作废**，压力全打到数据库——和「缓存雪崩」是同一个灾难。

**一致性哈希的思路**：不用「取模」这种脆弱映射，而是把机器和请求都放到一个「圆环」上：

```
想象一个首尾相接的大圆环（0 ~ 2^32-1）
把 A/B/C 三台机器 hash 后「钉」在环上的三个点
每个请求 key 也 hash 到环上一个点
然后「顺时针」找到离它最近的那台机器，发给它
```

**加一台机器 D 时**：

| 方案 | 加机器后 |
|:---|:---|
| 普通取模 `hash % N` | 几乎所有 key 都换机器，缓存全失效 |
| 一致性哈希 | 只有「D 顺时针方向上一小段」key 从 C 迁到 D，其余不动 |

理想情况 3 台变 4 台，只有约 1/4 的 key 迁移，剩下 3/4 缓存还命中原机器——缓存基本不失效。

> 前端类比：一致性哈希 ≈ 给数据「分片」，同一个 key 永远落同一个桶，桶数量变了也只影响一小部分 key，而不是全部重分。

**四张策略一句话对比**：

| 策略 | 判断依据 | 一句话 |
|:---|:---|:---|
| 轮询 | 轮流发 | 不管谁忙，一人一张发牌 |
| 加权轮询 | 按权重分 | 强机器多分、弱机器少分 |
| 最少连接数 | 看谁最闲 | 谁有空发谁，适合耗时差异大 |
| 一致性哈希 | 按 key 固定落点 | 加机器时缓存不失效 |

## 5. 负载均衡在哪一层做

| 层 | 实现 | 特点 |
|:---|:---|:---|
| **DNS 层** | DNS 轮询解析到不同 IP | 最简单，但控制粗、不健康检查 |
| **硬件负载均衡** | F5 等专用设备 | 性能强、超贵，大厂用 |
| **软件负载均衡** | Nginx / LVS / HAProxy | 最常用，便宜灵活 |
| **网关/应用层** | 云网关、K8s Service、微服务网关 | 云原生时代主流 |

> 生产上最常见的是 **Nginx 做入口负载均衡 + K8s Service 做服务间负载均衡**。

## 6. 横向扩展的前提：无状态（关键！）

负载均衡要求「同一个请求打到任何一台机器，结果都一样」。这就要求服务是**无状态（Stateless）**的——不把「用户会话」存在单台机器内存里。

**如果存了状态会怎样**：用户第一次打到机器 A，session 存在 A 里；第二次被负载均衡到机器 B，B 上没有这个 session → 用户「被登出」。这就是「有状态」导致的问题。

**两种解法**：

| 方案 | 做法 | 特点 |
|:---|:---|:---|
| **Session 共享** | 把 session 统一存 Redis，各机器都去 Redis 读 | 推荐，机器可任意扩展 |
| **会话保持（粘性会话）** | 同一用户固定打到同一台（IP hash） | 简单，但机器挂了会话就丢 |

> **前端类比**：无状态 ≈ React 的「函数式组件 + 纯函数」——不依赖外部可变状态，放哪渲染结果都一样。后端服务做「无状态」，才能放心地加机器、随便分。

## 7. LLM 场景的特殊点：负载的是 GPU

传统后端的负载均衡看「CPU / 连接数」，LLM 服务看的是「**GPU 显存和利用率**」，这带来两个特殊点：

1. **GPU 比 CPU 稀缺得多**：一台机器可能只有 1~4 张卡，每张卡能同时跑几个模型实例都有限。所以「加机器」对 LLM 服务更贵、更敏感。
2. **负载维度不同**：调度时要看「哪台机器的 GPU 显存还有余量、哪个模型实例的空闲 slot 多」，而不是简单轮询。

**LLM 服务的水平扩展**：同一模型部署多个副本（多个 vLLM 实例），前面加负载均衡分发。这对应工程化专项 4.2 的 vLLM 部署 + 4.11 的多实例高可用。

> **前端类比**：GPU 负载均衡 ≈ 前端「把重计算任务分发给多个 Web Worker」，调度时要看哪个 Worker 空闲，而不是无脑轮询。

## 8. 高可用（HA）—— 负载均衡的隐藏作用

高可用（High Availability）核心是「**单点故障（Single Point of Failure）不致命**」：

- **健康检查**：负载均衡器定时探活每台机器，挂了就剔除。
- **故障转移**：机器 A 挂了，它的流量自动切到 B、C，用户无感。
- **多副本 + 灾备**：不只应用多副本，负载均衡器、数据库、Redis 都不能是单点。

> 面试讲「高可用」就答这几个词：**多实例 + 负载均衡 + 健康检查 + 故障转移 + 灾备**。

## 9. 面试怎么讲

> "扛高并发最后一步是横向扩展 + 负载均衡。单机有天花板，所以部署多实例，前面放负载均衡器（Nginx 或 K8s Service）分发流量。策略上用轮询或最少连接数，加机器时用一致性哈希减少缓存失效。前提是服务无状态，session 放 Redis 共享。负载均衡不只是分摊，还承担高可用——健康检查发现某台挂了就剔除、流量切换，保证单点故障不影响用户。LLM 服务特殊在负载的是 GPU，调度要看显存余量和实例空闲槽位。"
