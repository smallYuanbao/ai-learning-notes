# 微调概念与 LoRA 原理

> 📅 学习日期：2026-08-11 ~ 2026-08-12
> 🔗 关联面试题：微调专题 题1、2、3、4、5、6、9、10、11、12、13、15、16、17、18、19、20、21

## 1. 为什么你手里的通用大模型总是不听话？

### 1.1 一个让你感同身受的场景

你拿到一个顶级的通用大模型（GPT-4o / DeepSeek-V3 / Claude 3.5）。你满心期待它能帮你：

- 按照你公司的格式规范写周报
- 模仿你的语气回复客户邮件
- 准确判断你们行业特有的业务逻辑

然后你开始测试。

你试了各种 Prompt 技巧：Few-shot、Chain-of-Thought、角色扮演……

结果呢？

有时候管用。有时候不管用。你改一下 Prompt，管用了一次。下次换个问法，又不管用了。

**你开始意识到一个问题：提示词优化，是一条走到黑的死胡同。**


### 1.2 提示词工程能做到什么，做不到什么？

| 能做的 | 做不到的 |
| :--- | :--- |
| 临时引导模型的回答方向 | 让模型稳定记住某个特定领域的“套路” |
| 给模型提供上下文的示例 | 让模型的默认行为发生根本性改变 |
| 让模型在单次对话中表现更好 | 让模型在所有对话中都保持一致的风格 |
| 告诉模型“你应该像这样回答” | 让模型内化为“我的默认风格就是这样” |

**不是说 Prompt 每次都传就能解决吗？—— 理论上对，实际上稳不住。四个原因：**

1. **Prompt 是外部指令，不是模型的"本能"**。每次传 Prompt 等于每次对模型说一遍"请按这个格式来"。模型听了，大多数时候遵守，但它本质是在**模式匹配**——换一个稍微不同的问法（"帮我看看这份合同" vs "审计一下风险点"），同样的 Prompt 可能产生细微偏差。

2. **Prompt 越长，约束力越弱**。Few-shot 示例 + 格式要求 + 输出规范全写进去，Prompt 膨胀到几千 Token。模型对 Prompt 后半段的注意力会稀释，开始"选择性忽略"一些约束。

3. **换模型版本，Prompt 可能失效**。用 DeepSeek v2 调试好的 Prompt，升级 v3 后可能跑偏——不是你的 Prompt 没写好，是模型的内部表示变了，对同一条指令的理解产生了差异。

4. **多轮对话中约束会衰减**。Agent 场景下，对话历史越长，System Prompt 的约束力就越弱——模型越来越"听自己的"，而不是听 Prompt 的。

> **结论**：提示词能做到"大多数时候管用"，但做不到"不需要再操心了"。提示词是"临时指挥"，微调是"性格重塑"。


### 1.3 一个真实的业务困境

假设你需要模型帮你**审核合同**。你的要求：
- 识别出合同中缺失的关键条款
- 用你公司特有的格式输出审计结果
- 不要长篇大论，只给结论和风险点

你写了一个精致的 Prompt，塞了 3 个 Few-shot 示例。测试了 10 份合同，效果不错。

但是：
- 换了 10 份合同，格式跑偏了
- 换了个模型的版本，格式跑偏了
- 明天来了一个新实习生（换了模型），格式跑偏了
- 你甚至自己忘记把 Few-shot 示例写全，格式跑偏了

**你会发现：Prompt 是你的“咒语”，但模型随时可以换一套咒语规则。**


### 1.4 核心问题暴露：模型没有学会“你的规则”

大模型的预训练目标是让它**读懂了全世界**，但这不意味着它**学会了你的独特要求**。

- 它知道“审核合同”是什么意思
- 但它不知道 **“你公司审核合同的格式要求”**

这两个之间，隔着一层叫做 **“私有化行为约束”** 的东西。

> **预训练模型是“通用大脑”，你需要的是“你公司的专属大脑”。**


### 1.5 两种解法

面对这个“模型不听话”的问题，主流有两个方向：

| 方案 | 怎么做 | 适用场景 |
| :--- | :--- | :--- |
| **RAG（检索增强生成）** | 外部挂载知识库，让模型“临时查资料” | 需要大量动态知识（财报、FAQ、政策文档） |
| **微调（Fine-tuning）** | 在模型内部调整权重，让模型“改变默认行为” | 需要稳定风格、固定格式、特定逻辑推理 |

它们解决的是**不同层面**的问题：

- **RAG**：解决的是“信息不足”——模型不知道这件具体的事。
- **微调**：解决的是“行为不对”——模型知道这件事，但它不是按你的方式做的。

> **这里我们只专注微调。因为你的问题不是“模型不知道合同是什么”，而是“它不按你的格式输出”。**


### 1.6 所以微调到底是什么？

你现在已经知道它要解决什么问题了。一句话定义：

> **微调（Fine-tuning）**：在已经预训练好的大模型上，用你自己的数据再训练一小段，让模型把”你的规则”从外部 Prompt 指令变成内部默认行为。

展开说就是三件事：

| | 做什么 | 效果 |
|:---|------|------|
| **输入** | 准备你自己的数据（几百到几千条格式正确的示例） | 不需要海量数据，只需要”示范” |
| **过程** | 在预训练模型上继续训练一小段 | 不从头训，只是在”地基”上”装修” |
| **输出** | 模型不再需要你每次传复杂 Prompt | 你不再需要写 Few-shot、不需要祈祷格式稳定 |

> **本质：微调做的不是”教模型新知识”，而是”教模型你的做事方式”。**

读完这一章，你应该能用一句话跟别人说清楚微调是什么了。第二章我们会展开细节——用类比帮你建立直觉，用对比表帮你理清预训练和微调的关系。


### 1.7 但你可能会想：这听起来很贵啊？

读到这儿，你的脑子里很可能冒出两个问题：

**问题一：「微调听起来要训练，那是不是要很多显卡？」**
是的。全量微调（Full Fine-tuning）需要更新模型的全部参数。对于 7B、13B 甚至 70B 的大模型，这需要多张高性能 GPU，动辄几十到几百 GB 的显存。

**问题二：「那如果我只想在自己的单卡上试一下呢？」**
这是一个非常实际的问题。全量微调的硬件门槛，把大多数个人开发者挡在了门外。

> **这个问题的解法，就是我们第 4 章要学的 LoRA。但在那之前，我们需要先搞清楚：全量微调到底贵在哪？以及有没有什么妥协方案？**


## 2. 微调到底在“调”什么？—— 从直觉到定义

### 2.1 先放下技术，从生活直觉开始

想象一下，你要培养一个能帮你处理法律文件的超级助理。

**第一步：通识教育（预训练阶段）**
你让他从小读遍全世界的书——语文、数学、历史、科学、文学……他掌握了人类通用的语言能力、逻辑推理和常识。现在，他是一个**知识渊博的大学毕业生**。

他能跟你聊任何话题，但你让他起草一份“股权转让协议”，他写不出来。他不懂法律术语，不知道合同的格式，也不清楚哪些条款是必须的。

**第二步：专业培训（微调阶段）**
你把他送进一家律师事务所实习。他不需要从小学重新读起，只需要**精读大量的法律文书、判决书、合同模板**。经过一段时间的“专业培训”，他学会了法律领域的“行话”和“套路”，现在能起草合格的合同了。

> **微调，就是大模型的“专业培训”。**


### 2.2 回到技术定义——那四个关键词到底在说什么

第一章我们给了微调一个一句话定义。现在拆开看每个关键词到底是什么意思：

> **回顾定义**：在已经预训练好的大模型基础上，使用**特定领域的小规模数据集**，对模型进行**额外的训练**，使其在该领域的表现更加精准和专业。

**拆解关键词：**
- **预训练好的大模型**：已经读完了“全世界书籍”的基础模型（如 GPT、DeepSeek 等）。
- **特定领域的小规模数据集**：比如法律文书、医学病历、代码片段、客服对话等。
- **额外的训练**：让模型继续学习，但学习量很小，只是“精读”而非“通读”。
- **表现更精准**：模型还是那个模型，但更擅长某个特定任务了。


### 2.3 预训练 vs 微调：两张对比表

#### 表1：宏观对比（从“人”的视角）

| 维度 | **预训练（Pre-training）** | **微调（Fine-tuning）** |
| :--- | :--- | :--- |
| **类比** | 从小学读到大学毕业 | 入职后的岗前专业培训 |
| **数据规模** | 海量（万亿级 Token） | 少量（几千 ~ 几万条样本） |
| **训练成本** | 极高（几千万美元） | 相对较低（几百到几千美元） |
| **产出** | 一个“通用”的大模型 | 一个“专精”的大模型 |
| **谁来做** | 大公司（OpenAI、DeepSeek） | 中小公司、开发者、甚至个人 |

#### 表2：技术对比（从“模型”的视角）

| 维度 | **预训练** | **微调** |
| :--- | :--- | :--- |
| **训练数据量** | 万亿级（TB 级别） | 百万级 Token 以内（MB~GB 级别） |
| **训练轮数** | 1~2 轮 | 3~10 轮 |
| **学习率（Learning Rate）** | 较大 | **极小**（防止”灾难性遗忘”） |
| **参数量变化** | 所有参数从随机初始化开始训练 | 所有参数在预训练基础上**微调** |

> **插一句：学习率是什么？**
>
> 训练模型 = 不断调权重，让输出越来越接近正确答案。学习率就是**每次调整的”步长”**。
>
> - 类比：你在调一台老式收音机的旋钮找电台。预训练 = 一开始不知道电台在哪，你可以**大步拧**（高学习率），快速接近目标。微调 = 你已经很接近了，只是微调一点点让声音更清晰，这时**只能小步微拧**（低学习率）——拧大了反而会跑偏，把原本已经收到的台弄丢了。
> - 为什么微调用**极小**的学习率？因为预训练模型的权重已经是”接近最优”的状态了。大步调整 = 把已经学到的通用能力”震碎”——这就是表里提到的**灾难性遗忘**：模型学会了你的格式，但忘了怎么正常说话。

> **核心结论**：**预训练是”从零到一”，微调是”从一到专”。**


### 2.4 为什么不全量训练，非要“预训练+微调”两步走？

答案很简单：**成本。**

| 方案 | 假设 | 成本估算 |
| :--- | :--- | :--- |
| **从头训练 GPT-3（175B）** | 1 万张 A100，3~4 个月 | 约 **5000 万 ~ 1 亿美元** |
| **对 GPT-3 进行微调** | 1 张 A100，1~3 天 | 约 **500 ~ 2000 美元** |

> **差距：10 万倍。**

这就是为什么“预训练+微调”成为行业标准范式。**大公司花巨资造“地基”（预训练），中小公司在“地基”上盖“房子”（微调）。**


### 2.5 微调后，模型到底“变”了什么？

回到你的基础知识（Transformer 里的权重矩阵）：

- **预训练模型**：所有权重矩阵（`W_Q`、`W_K`、`W_V`、`W_1`、`W_2` 等）里的数字，都是**经过海量数据训练后收敛的值**，它们共同存储了“通用知识”。
- **微调过程**：让模型在特定数据上继续做**反向传播 + 梯度下降**。每次更新时，所有权重矩阵里的数字都会被**极其微小地调整**。
- **微调结果**：权重的数值变化非常小（因为学习率很低），但这些**极其微小**的变化，却能让模型的输出分布明显偏向“你期望的方向”。

> **类比**：预训练模型是一张**精准的全球地图**。微调是在这个地图上，把你所在的城市**放大、标注细节、加上路况信息**。全球地图没变，但你对这个城市的了解变得**极其精细**。


### 2.6 本章小结

| # | 核心要点 | 一句话说明 |
| :--- | :--- | :--- |
| 1 | **微调是什么** | 让预训练好的大模型在特定领域继续学习，成为“专家” |
| 2 | **两阶段范式** | 预训练（造地基）→ 微调（盖房子） |
| 3 | **核心差异** | 预训练消耗亿级成本，微调只需千元级别 |
| 4 | **模型变化** | 所有权重矩阵被微小调整，输出更偏向特定任务 |
| 5 | **关键约束** | 学习率必须极小，防止“灾难性遗忘” |


## 3. 全量微调到底贵在哪？

### 3.1 回顾一下我们走到了哪

- **第 1 章**：我们确定了问题——通用大模型不听话，Prompt 治标不治本。
- **第 2 章**：我们确定了方向——微调能让模型内化“你的规则”，变成“你公司的专属大脑”。
- **第 2 章末尾**：我们留了一个钩子——“微调听起来要训练，那是不是很贵？”

现在，我们来回答这个问题。

### 3.2 全量微调（Full Fine-tuning）到底在做什么？

先看一张图（脑补）：
输入: “请审核这份合同”
↓
[嵌入层] → [Transformer 层 1] → [Transformer 层 2] → ... → [Transformer 层 N] → [输出层]
↑ ↑ ↑ ↑
需要更新 需要更新 需要更新 需要更新


**全量微调的本质是**：

> **当模型做错时（输出偏离你的期望），通过反向传播计算出每个层、每个神经元的“错误贡献度”，然后调整**所有权重矩阵里的每一个数字**，让下次输出更接近你的期望。**

你在基础篇学过：
- 每个 Transformer 层都有 `W_Q`、`W_K`、`W_V`、`W_1`、`W_2` 等多个权重矩阵
- 对于一个 7B 参数的模型，这意味着 **70 亿个数字需要被微调**
- 对于 70B 参数的模型，这是 **700 亿个数字**

**全量微调，就是同时调整这几十亿到几百亿个“旋钮”。**

### 3.3 全量微调的三个致命痛点

#### 痛点 1：显存不够（硬件门槛）

全量微调需要同时存储：
- 模型本身的参数（比如 7B 模型约 14GB — FP16 精度下每个参数占 2 字节，70B 约 140GB）
- 每个参数的梯度（跟参数一样大，又一份 14GB）
- 优化器状态（比如 Adam 优化器需要存两份动量，又是 2 倍）
- 中间激活值（Batch 里每条数据都要存）

**合计**：7B 模型全量微调大约需要 **60-80GB 显存**。这意味着你至少需要：
- 1 张 A100（80GB）—— 租用约 $2-3/小时
- 或者 2 张 RTX 4090（24GB × 2）—— 硬件投资 ~3 万人民币

> **个人开发者、学生、小团队：直接被挡在门外。**

#### 痛点 2：时间成本太高（训练时长）

全量微调要更新所有参数，意味着每次反向传播都要计算整个网络的梯度。

- 7B 模型全量微调：在单张 A100 上约需 **1-3 天**
- 70B 模型全量微调：需要多卡并行，约需 **数天到一周**

**每次想尝试一个新 idea，都要等几天才能看到结果。**

> **迭代速度 = 学习速度。全量微调的慢，本质上是在拖慢你的试错。**

#### 痛点 3：灾难性遗忘（Catastrophic Forgetting）

这是一个很隐蔽但很致命的问题。

> **当模型拼命学习新任务时，它可能会“忘记”之前学会的通用知识。**

现象：
- 你微调模型让它学会审核合同
- 微调后，审核合同能力提升了
- 但模型突然不会做算术题了，或者写诗变差了

> **就像一个律师，精通了公司法，但突然忘了怎么写简单的英文邮件。** 

具体怎么防？有四种手段，前三条只能「缓解」，真正「根除」要靠第 4 章的 PEFT 冻结：

#### 怎么防：四种手段，从缓解到根除

1. **极小学习率**：权重只做「小步微调」，不会把通用知识「震碎」。这是最基本的约束。

2. **数据回放（Replay）**：微调数据里混入一部分旧任务 / 预训练数据，让模型「边学新、边复习旧」。上面说的「精心设计的数据配比」指的就是它。

3. **正则化（EWC，Elastic Weight Consolidation）**：给「对旧任务重要」的权重加约束，限制它们偏移太大。核心思想是「重要的权重别乱动」。

4. **冻结原权重（PEFT / LoRA）**：最根本的手段——原权重完全不动，通用能力天然保留。这个第 4 章会重点展开。

> 前三条是「全量微调内部的缓解手段」，第四条是「换一种微调方式」。工程上主用第四条，因为前三者只能缓解、不能根除。

### 3.4 为什么全量微调这么“重”？一张表说清

| 痛点 | 具体表现 | 对开发者的影响 |
| :--- | :--- | :--- |
| **显存爆炸** | 需要 60-80GB 显存 | 买不起 A100，租不起长期实验 |
| **训练缓慢** | 单次微调 1-3 天 | 试错成本极高，不敢轻易尝试 |
| **灾难性遗忘** | 学新忘旧 | 微调后的模型可能在其他任务上变差 |
| **存储开销** | 每个微调任务产生一个完整的模型副本（14GB+） | 无法为每个场景保存多个专属模型 |

### 3.5 那么，业界是怎么解决这些问题的？

你可能会想：
- **显存不够** → 用更多显卡？（成本更高）
- **训练太慢** → 买更好的显卡？（治标不治本）
- **灾难性遗忘** → 更小的学习率？（效果有限）

这些问题都存在，但它们的共同点是：

> **它们都是“全量微调”这个方案本身的固有缺陷。** 只要你要调整所有参数，这些成本就躲不掉。

所以，**真正的解法不是“优化全量微调”，而是“换一种微调方式”。**

### 3.6 本章总结

| 问题 | 答案 |
| :--- | :--- |
| 全量微调贵在哪？ | 显存（60-80GB）、时间（1-3天）、存储（完整模型副本） |
| 灾难性遗忘是什么？ | 模型学新任务时忘掉旧知识 |
| 这些问题的根源是什么？ | 全量微调要动**所有**参数 |
| 怎么办？ | 需要一种**参数高效**的微调方法 |

> **全量微调的问题是：你想修一条路，但它让你重建整个城市。**

下一章我们要学的 LoRA，它的思路是：

> **“不重建城市，只在你需要的地方铺一条捷径。”**

📌 准备好从“修城市”切换到“铺捷径”了吗？我们进入第 4 章。


## 4. LoRA——用一条「旁路」解决问题

### 4.0 微调方法全景：先分两大类，再聚焦 LoRA

在正式学 LoRA 之前，先把「微调方法」这张地图铺开——你才不会以为"微调就只有 LoRA 一种"。

微调方法有**两条分类轴**：

- **按「改多少参数」分**：全量微调 vs 参数高效微调（PEFT）——这是本节要讲的第一条轴
- **按「怎么监督」分**：SFT vs RLHF——这是第 7 章要讲的第二条轴

> 两条轴是**正交**的，可以交叉组合：比如"用 LoRA 做 SFT""用 PPO 做 RLHF"。

#### 一、全量微调（Full Fine-Tuning）

更新模型的**全部参数**。第 3 章已经讲过它的三痛点了，这里只放一个缩略：

| 方法 | 改什么 | 特点 |
| :--- | :--- | :--- |
| **全量微调** | 全部参数 | 效果上限最高，但显存 / 时间 / 灾难性遗忘三大痛点 |
| **部分微调**（变体） | 只训最后几层 | 全量的"省电版"：冻前面层、只训后面 |

#### 二、参数高效微调（PEFT，Parameter-Efficient Fine-Tuning）

只更新**不到 1% 的参数**，就能逼近全量微调的效果。这是当前的主流方向，里面最火的是 LoRA：

| 方法 | 思路 | 一句话 |
| :--- | :--- | :--- |
| **LoRA** | 旁路 A×B 低秩矩阵 | 主流，不增推理延迟、可无损合并 |
| **Adapter** | 层间插入小模块 | 老牌，但会加推理延迟 |
| **Prefix-Tuning** | 输入前加可训练前缀 | 会占用输入长度 |
| **Prompt-Tuning** | 只训几个软 token | 最轻，但表达力弱 |
| **QLoRA** | LoRA + 4-bit 量化 | 显存再降，单卡可跑 |
| **BitFit** | 只训 bias | 参数量最小 |

> **为什么这章只讲 LoRA？** 因为它是当前工程实践里最主流、最均衡的选择——效果接近全量微调，却不增加推理延迟、适配器只有几 MB。剩下的方法你记个名字和一句话，面试被问到时能对号入座即可。

现在我们聚焦 LoRA，从头把它讲透。

### 4.1 连接上一章的钩子

上一章我们说了全量微调的三个痛点：
- 显存要 60-80GB
- 训练要 1-3 天
- 产生一个完整的模型副本（几十 GB）

现在问题摆在面前：

> **全量微调这么贵，有没有一种方法，能在单张普通显卡上、几小时内完成微调，而且不会产生灾难性遗忘？**

2021 年，微软的研究团队在论文 **《LoRA: Low-Rank Adaptation of Large Language Models》** 中给出了一种答案。

**LoRA = Low-Rank Adaptation（低秩适应）**

它的核心思想可以用一句话概括：

> **“不修改原模型，在旁边加一条小路来学新知识。小路很小，成本极低，学完之后可以并入主路。”**

### 4.2 一个直观类比：主干道 vs 临时通道

想象一下城市交通：

**全量微调 = 改建整条主干道**
- 需要封闭施工（不能同时用旧路）
- 花费巨大（全城人力物力）
- 改建完成后，原来会走这条路的车也被迫改道（灾难性遗忘）

**LoRA = 在旁边修一条临时匝道**
- 主干道正常通车（原模型能力不变）
- 只在需要转向的地方铺一小段路（只训练旁路）
- 施工完成，匝道并入主干道（合并权重，无额外推理成本）

> **LoRA 的哲学：你不需要改造整个大脑，只需要在关键部位加一个“外挂模块”。**

### 4.3 为什么能省参数？（直觉层）

我们先把复杂的数学放一边。

在神经网络中，权重矩阵（比如 `W`）负责把输入转换成输出。全量微调要调整 `W` 里的**每一个数字**。

LoRA 的想法是：

> **当模型学习一个新任务时，真正发生变化的地方，可能只占整个矩阵的一小部分。** 这个变化的“方向”可以压缩成一个很小的矩阵。

**LoRA 不直接修改 `W`，而是在旁边加两个小矩阵 `A` 和 `B`：**

原始路径：输出 = W × 输入

LoRA 路径：输出 = (W + A × B) × 输入
↑ ↑
原模型不动 新增的“旁路”


- `W` 是原来的大矩阵（比如 1000 × 1000，100 万个参数）
- `A` 是一个小矩阵（1000 × 8）
- `B` 是一个小矩阵（8 × 1000）
- `A × B` 的结果是 1000 × 1000，**但 A 和 B 加起来只有 16,000 个参数**

> 真实的 Transformer 权重矩阵远大于 1000×1000（比如 4096×4096），这里只是简化演示。矩阵越大，LoRA 的压缩效果越惊人。

> **需要训练的从 100 万个参数，降到了 1.6 万个参数。**

### 4.4 这个“8”是什么？（秩的概念）

在上面 `A` 是 `1000 × 8`，`B` 是 `8 × 1000`。这个 **8** 就是 LoRA 的核心超参数：**秩（Rank，记作 r）**。

它决定了旁路的“容量”：

| 秩（r） | 可训练参数量（原矩阵 1000×1000） | 表达能力 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **1** | 2,000 | 很弱 | 极简单的风格迁移 |
| **4** | 8,000 | 较弱 | 轻量级任务适配 |
| **8** | 16,000 | **适中（最常用）** | 多数微调场景，平衡效果与成本 |
| **16** | 32,000 | 较强 | 复杂任务，数据量大时 |
| **64** | 128,000 | 很强 | 接近全量微调效果，但参数仍少很多 |

> **秩 r 决定了旁路的“宽度”：路越宽（r 越大），能学的信息越多，但训练成本也越高。** 
>
> 默认推荐 r=8 或 r=16，兼顾效果与效率。

### 4.5 训练过程中发生了什么？

**训练时**（你在做微调）：
1. 原模型 `W` **完全冻结**，不做任何更新（省显存）
2. 只训练 `A` 和 `B` 里的数字（参数量减少 98%）
3. 不需要存储整个模型的梯度，只存 `A` 和 `B` 的梯度

**推理时**（你使用模型）：
1. 计算 `W_new = W + A × B`
2. 把 `A × B` 的结果合并进 `W`
3. 丢弃 `A` 和 `B`
4. **推理速度和原模型完全一致**（没有任何额外开销）

> **训练时：多了一条小路，只修小路。推理时：小路并入主路，消失不见。**

### 4.6 LoRA 的四大优势

现在我们可以用第 3 章的三个痛点来对照：

| 痛点 | 全量微调 | LoRA |
| :--- | :--- | :--- |
| **显存需求** | 60-80GB（7B 模型） | **只需 ~12-16GB**（单张 3090/4090 可跑） |
| **训练时间** | 1-3 天 | **数小时（通常 2-6 小时）** |
| **模型存储** | 每个任务存一个完整模型（14GB+） | **每个任务只存 A+B 两个小矩阵（几 MB 到几十 MB）** |
| **灾难性遗忘** | 容易发生 | **不会发生（原模型完全不改）** |

**让人兴奋的地方**：你可以为一个模型训练多个 LoRA 模块（每个几 MB），在推理时根据任务随时切换，而不需要加载多个大模型。

> **极简类比**：全量微调是“重塑大脑”；LoRA 是“换一副眼镜”。不同的任务换不同的眼镜，大脑本身不用重装。

| 2 | **核心思想** | 在原权重旁增加小矩阵 A×B 作为旁路，只训练旁路 |

### 5.4 阶段 1 详解：数据到底长什么样？

这是初学者最容易卡住的地方——因为网上教程默认你知道数据格式，但没人告诉你它为什么长这样。

#### 5.4.1 你需要的是一堆“对话模板”

假设你想让模型学会按你的格式写“周报”。

你需要准备的数据是 **“输入 → 期望输出”** 的对：

- 输入：“我这周做了用户登录功能的开发、修复了 3 个 Bug、参加了两场会议”
- 输出：
📋 周报
【开发】完成用户登录模块的前后端联调
【修复】修复线上 Bug 3 个
【会议】参与项目同步会 ×2


> **微调的核心就是：给模型看大量这样的“对话范例”，让它学会“当用户用这种语气提问时，你应该按哪种格式回复”。**

#### 5.4.2 标准格式：Alpaca 格式

最常用的训练数据格式是 Alpaca 格式（源于斯坦福的 Alpaca 模型）。它长这样：

```json
{
  "instruction": "按周报格式总结我本周的工作内容",
  "input": "我这周做了用户登录功能的开发、修复了 3 个 Bug、参加了两场会议",
  "output": "📋 周报\n【开发】完成用户登录模块的前后端联调\n【修复】修复线上 Bug 3 个\n【会议】参与项目同步会 ×2"
}
```

| 字段 | 含义 | 是否必填 |
| :--- | :--- | :---: |
| `instruction` | 任务的指令描述 | ✅ 是 |
| `input` | 可选的具体输入内容 | ❌ 否 |
| `output` | 期望的模型输出（答案） | ✅ 是 |


**实际场景中：**

- 如果你的任务简单（比如“把英文翻译成中文”），可以用 instruction 放原文，output 放译文，input 置空

- 如果你的任务需要上下文（比如“根据这段对话总结要点”），就把上下文放 input

#### 5.4.3 一条重要的原则：数据质量 > 数据数量
初学者最常见的误区是：“我要准备 10 万条数据才能微调。”

**事实是：**

- 几百条高质量数据 → 模型已经能学会“格式和风格”

- 几千条数据 → 模型能学会“更复杂的逻辑和规则”

- 几万条数据 → 通常是过度收集，边际收益递减

> 500 条格式规范、覆盖全面的数据，远胜过 10000 条随意的、格式混乱的数据。

为什么？因为 LoRA 本身要学的东西很简单——它不需要重新学习“语言”，只需要学会“你的规则”。少量但高质量的数据已经足够了。

> ⚠️ **数据准备的三个常见坑：**
>
> 1. **用 ChatGPT 生成全部训练数据** — 结果模型学会了 ChatGPT 的语气和句式，而不是你公司产品的口吻。
> 2. **只喂「标准问法」** — 训练数据里全是「请帮我审核这份合同」，上线后用户说「帮我看下这个合同有没有问题」模型就不认识了。**输入要覆盖多种变体。**
> 3. **同一条输入对应两种不同输出** — 比如同样的合同内容，一条数据里标了「缺少保密条款」，另一条标了「缺少违约责任条款」——模型会困惑到底该输出哪个，最终两个都学不会。

### 5.5 阶段 2 详解：LoRA 配置参数（它们是什么意思？）
当你使用 PEFT 库配置 LoRA 时，会看到这样一段代码：

```python
from peft import LoraConfig

lora_config = LoraConfig(
    r=8,
    lora_alpha=16,
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM"
)
```

这些参数是什么意思？我们用第 4 章的直觉来理解：

| 参数 | 含义 | 直觉解释 |
| :--- | :--- | :--- |
| `r`（秩） | 旁路矩阵的维度（A 的列数 / B 的行数） | **路的宽度**。r=8 是中等宽度，能学的内容适中；r=16 更宽，能学更多细节但成本更高 |
| `lora_alpha` | LoRA 的缩放系数 | **路的作用强度**。alpha 越大，旁路的影响力越大；通常设为 r 的 2 倍（经验值），比如 r=8 时 alpha=16 |
| `target_modules` | 对模型的哪些层应用 LoRA | **在哪条路上修旁路**。通常针对注意力层的 `q_proj`（Query）和 `v_proj`（Value），这是最有效的位置 |
| `lora_dropout` | 训练时随机丢弃部分旁路连接 | **防止旁路过拟合**。0.05 表示每次训练有 5% 的连接临时关闭，避免”太依赖某一条特定路线” |
| `bias` | 是否训练偏置参数 | **是否连偏移量一起调**。通常设为 `”none”`，即不训练偏置，进一步省参数 |

#### 5.5.1 最重要的参数组合：r 和 lora_alpha
这俩参数共同决定了“旁路学得多用力”：

| 设置 | 效果 | 适用场景 |
| :--- | :--- | :--- |
| `r=4, alpha=8` | 小路很窄，但作用适度 | 数据少（< 500 条）、任务简单（如风格迁移） |
| `r=8, alpha=16` | 🏆 经典默认配置 | 大部分场景：数据中等（1000-5000 条）、通用任务 |
| `r=16, alpha=32` | 路较宽，学得更多 | 数据多（> 5000 条）、复杂任务（带推理逻辑） |
| `r=64, alpha=128` | 接近全量微调效果 | 数据量大、追求极致效果（但失去了 LoRA 的省参数优势） |

> 快速上手公式：lora_alpha = 2 × r，从头到尾只用 r=8/alpha=16 跑通流程就够了。

> **为什么 `target_modules` 通常只选 `q_proj` 和 `v_proj`？**
>
> 注意力机制中，**Query** 决定「我要找什么」，**Value** 决定「我输出什么」——这是对模型输出分布影响最大的两个环节。`k_proj`（Key，用于匹配打分）和 `o_proj`（Output 投影层）的影响相对次要，加上 LoRA 收益不大，反而增加参数开销。所以业界默认只对 Q 和 V 加旁路，性价比最高。

```
╔═══════════════════════════════════════════════════════════════════╗  ║
║  ⚙️ 步骤 2 · 加载模型 + LoRA 配置                                 ║  ║
║                                                                   ║  ║
║  2.1  加载预训练模型（如 Qwen-7B）                                 ║  ║
║  2.2  配置 LoraConfig(r=8, alpha=16, target_modules=[...])       ║  ║
║  2.3  用 PEFT 把 LoRA 附加到模型上                                ║  ║
║  2.4  此时原模型参数冻结，仅 LoRA 新增的小矩阵被标记为「可训练」   ║  ║
╚══════════════════════════════════════════════════════╗              ║
                                                       ║              ║
                                                       ▼              ║
╔═══════════════════════════════════════════════════════════════════╗  ║
║  🏃 步骤 3 · 训练                                                 ║  ║
║                                                                   ║  ║
║  3.1  把数据切成批次（Batch）输入模型                              ║  ║
║  3.2  模型做前向传播（预测输出）                                   ║  ║
║  3.3  计算预测值与期望输出的差距（Loss）                           ║  ║
║  3.4  反向传播 → 只更新 LoRA 的 A 和 B 矩阵（原模型完全不动）      ║  ║
║  3.5  重复 3.1–3.4，直到 Loss 收敛（通常 1–5 个 Epoch）           ║  ║
╚══════════════════════════════════════════════════════╗              ║
                                                       ║              ║
                                                       ▼              ║
╔═══════════════════════════════════════════════════════════════════╗  ║
║  🚀 步骤 4 · 保存与推理                                           ║  ║
║                                                                   ║  ║
║  4.1  保存训练好的 LoRA 适配器（几 MB 的 .bin / .safetensors）    ║  ║
║  4.2  推理时加载原模型 + 加载 LoRA 适配器                          ║  ║
║  4.3  或 merge_and_unload() 合并回原模型，得到一个完整新模型       ║  ║
╚═══════════════════════════════════════════════════════════════════╝

```

每一步的时间估算（以 7B 模型 + 单张 4090 为例）：

- 准备数据：1-3 小时（取决于你的数据复杂度）

- 加载模型 + 配置：5-10 分钟

- 训练（1000 条数据，3 个 Epoch）：约 2-4 小时

- 保存与推理：5-10 分钟

### 6.3 完整代码（可直接运行）

以下是完整的 LoRA 微调脚本。我们使用 **Qwen2.5-0.5B** 作为示例模型——它足够小，可以在消费级显卡上快速跑通，让你先看到完整流程[reference:3]。

你可以把这段代码保存为 `train_lora.py`，然后在命令行执行 `python train_lora.py`。

```python
# train_lora.py
# 你的第一个 LoRA 微调脚本

import torch
from transformers import (
    AutoModelForCausalLM,
    AutoTokenizer,
    TrainingArguments,
    Trainer,
    DataCollatorForSeq2Seq
)
from peft import LoraConfig, get_peft_model, TaskType
from datasets import load_dataset
import json

# ============================================================
# 第 1 步：加载模型和分词器
# ============================================================

model_name = "Qwen/Qwen2.5-0.5B-Instruct"  # 小模型，快速验证

print(f"正在加载模型: {model_name}")

tokenizer = AutoTokenizer.from_pretrained(model_name, trust_remote_code=True)
# 设置 pad_token，防止训练时警告
if tokenizer.pad_token is None:
    tokenizer.pad_token = tokenizer.eos_token

model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,  # 节省显存
    device_map="auto",           # 自动分配到可用设备
    trust_remote_code=True
)

# ============================================================
# 第 2 步：配置 LoRA
# ============================================================

lora_config = LoraConfig(
    r=8,                         # 秩（低秩维度）[reference:4]
    lora_alpha=16,               # 缩放系数，通常设为 r 的 2 倍[reference:5]
    target_modules=["q_proj", "v_proj"],  # 只对 Query 和 Value 层加旁路[reference:6]
    lora_dropout=0.05,           # 防止过拟合
    bias="none",                 # 不训练偏置
    task_type=TaskType.CAUSAL_LM # 因果语言模型（生成任务）[reference:7]
)

model = get_peft_model(model, lora_config)
model.print_trainable_parameters()  # 打印可训练参数量
# 输出示例: trainable params: 2,097,152 || all params: 500,000,000 || trainable%: 0.42%

# ============================================================
# 第 3 步：准备数据（Alpaca 格式）
# ============================================================

# 示例数据：让模型学会“用一句话总结一段文字”
# 实际使用时，你可以替换成自己的数据（JSONL 格式）[reference:8]
train_data = [
    {
        "instruction": "用一句话总结以下内容",
        "input": "人工智能是研究、开发用于模拟、延伸和扩展人类智能的理论、方法、技术及应用系统的一门新的技术科学。",
        "output": "人工智能是模拟和扩展人类智能的技术科学。"
    },
    {
        "instruction": "用一句话总结以下内容",
        "input": "深度学习是机器学习的一个分支领域，它通过多层神经网络来学习数据的表征，在图像识别、语音识别等领域取得了突破性进展。",
        "output": "深度学习通过多层神经网络学习数据表征，在图像和语音识别领域取得突破。"
    },
    # ... 更多数据（建议至少 100-500 条）
]

# 将数据保存为临时 JSONL 文件
with open("temp_train_data.jsonl", "w", encoding="utf-8") as f:
    for item in train_data:
        f.write(json.dumps(item, ensure_ascii=False) + "\n")

# 加载数据集
dataset = load_dataset("json", data_files="temp_train_data.jsonl")

# ============================================================
# 第 4 步：数据预处理（格式化 + Tokenization）
# ============================================================

def format_instruction(example):
    """将 Alpaca 格式转换为模型输入格式"""
    if example.get("input"):
        text = f"### 指令：{example['instruction']}\n### 输入：{example['input']}\n### 回答：{example['output']}"
    else:
        text = f"### 指令：{example['instruction']}\n### 回答：{example['output']}"
    return {"text": text}

def tokenize_function(examples):
    """对文本进行 Tokenization"""
    inputs = tokenizer(
        examples["text"],
        truncation=True,
        padding=False,
        max_length=512,          # 根据你的数据长度调整
        return_tensors=None
    )
    # 对于因果 LM，labels 就是 input_ids（预测下一个 token）
    inputs["labels"] = inputs["input_ids"].copy()
    return inputs

# 应用格式化 + Tokenization
dataset = dataset.map(format_instruction)
tokenized_dataset = dataset.map(
    tokenize_function,
    remove_columns=dataset["train"].column_names,
    batched=True
)

# ============================================================
# 第 5 步：配置训练参数并开始训练
# ============================================================

training_args = TrainingArguments(
    output_dir="./lora_output",          # 保存路径
    num_train_epochs=3,                  # 训练轮数
    per_device_train_batch_size=4,       # 批大小（根据显存调整）
    gradient_accumulation_steps=2,       # 梯度累积（等效 batch_size = 4*2 = 8）
    learning_rate=2e-4,                  # LoRA 常用学习率
    warmup_steps=10,
    logging_steps=10,
    save_steps=50,
    save_total_limit=2,
    fp16=True,                           # 混合精度训练，节省显存
    report_to="none",                    # 不向外部平台报告
)

trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=tokenized_dataset["train"],
    data_collator=DataCollatorForSeq2Seq(tokenizer=tokenizer, padding=True),
)

print("开始训练...")
trainer.train()

# ============================================================
# 第 6 步：保存 LoRA 适配器
# ============================================================

model.save_pretrained("./lora_adapter")
tokenizer.save_pretrained("./lora_adapter")
print("✅ LoRA 适配器已保存到 ./lora_adapter")

# ============================================================
# 第 7 步：推理测试（加载 LoRA 适配器进行推理）
# ============================================================

print("\n开始推理测试...")

from peft import PeftModel

# 重新加载基础模型
base_model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,
    device_map="auto",
    trust_remote_code=True
)

# 加载 LoRA 适配器
lora_model = PeftModel.from_pretrained(base_model, "./lora_adapter")

# 测试输入
test_prompt = "### 指令：用一句话总结以下内容\n### 输入：量子计算是一种利用量子力学原理进行信息处理的新型计算范式，在特定问题上具有远超经典计算机的计算能力。\n### 回答："

inputs = tokenizer(test_prompt, return_tensors="pt").to("cuda")
outputs = lora_model.generate(
    **inputs,
    max_new_tokens=128,
    temperature=0.7,
    do_sample=True
)
response = tokenizer.decode(outputs[0], skip_special_tokens=True)
print("模型回答：", response)

```

### 6.6 常见报错与解决方法

| 报错信息 | 可能原因 | 解决方法 |
| :--- | :--- | :--- |
| `CUDA out of memory` | 显存不足 | 减小 `per_device_train_batch_size`（如 4→2→1）；或启用 QLoRA（见 §6.7） |
| `bitsandbytes` 相关报错 | 量化库未安装 | `pip install bitsandbytes` |
| `Tokenizer pad_token not set` | 分词器未设置填充标记 | 添加 `tokenizer.pad_token = tokenizer.eos_token` |
| 训练很慢 | 数据量太大或 batch_size 太小 | 增加 `gradient_accumulation_steps`，或启用 `fp16=True` |
| 模型输出乱码 | 数据格式与模型对话模板不匹配 | 检查 `format_instruction` 中的模板是否符合该模型的 Chat Template |

### 6.7 如果你只有 8GB 显存：QLoRA

如果你的显卡显存小于 12GB，可以使用 QLoRA（4-bit 量化 + LoRA）。它把模型权重压缩到 4-bit，显存需求可以降到 **6GB** 以下。

只需要修改模型加载部分的代码：

```python
from transformers import BitsAndBytesConfig

# 配置 4-bit 量化[reference:16][reference:17]
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",          # 4-bit 量化类型[reference:18]
    bnb_4bit_compute_dtype=torch.bfloat16,  # 计算精度[reference:19]
    bnb_4bit_use_double_quant=True,     # 双重量化，进一步省显存[reference:20]
)

model = AutoModelForCausalLM.from_pretrained(
    model_name,
    quantization_config=bnb_config,     # 使用 4-bit 量化加载[reference:21]
    device_map="auto",
    trust_remote_code=True
)
```

**显存对比（7B 模型）：**

| 方法 | 显存需求 | 适用显卡 |
| :--- | :---: | :--- |
| 全量微调 | 60–80 GB | A100（多卡） |
| LoRA（16-bit） | 12–16 GB | RTX 4090 / 3090 |
| QLoRA（4-bit） | 4–8 GB | RTX 3060 / 4060 |

QLoRA 的效果与标准 LoRA 非常接近，但显存需求降低了一半以上。

## 7. SFT 与 RLHF——微调的两大流派

### 7.1 回顾：你第 6 章做的事叫什么？

你在第 6 章跑通了完整的微调流程：

```
准备 Alpaca 格式数据 → LoraConfig 配置 → Trainer 训练 → 保存适配器
```

这套流程在业界有一个正式的名字：**SFT（Supervised Fine-Tuning，监督微调）**。

> **SFT = 给模型看「输入 → 标准答案」的对子，让它反复练，直到自己也能输出正确答案。**

你笔记里的周报例子就是典型的 SFT：

```json
{"instruction": "按周报格式总结我的工作", "input": "做了登录功能、修了 3 个 Bug", "output": "📋 周报\n【开发】完成登录模块…"}
```

模型看了几百条这样的数据后，就学会了：「用户这样描述工作内容时，我应该输出那种格式」。

**SFT 的本质**：给标准答案，照着学。模型学会的是「怎么做对」。


### 7.2 SFT 的适用场景…和它的天花板

| SFT 擅长 | SFT 不擅长 |
| :--- | :--- |
| 格式化输出（周报、合同、邮件模板） | 「写一封得体的拒信」——没有唯一正确答案 |
| 特定风格迁移（模仿某人的语气） | 「给用户有同理心的回复」——好坏取决于人的感受 |
| 固定逻辑推理路径（按步骤分析） | 「解释这个概念时要通俗易懂」——什么是「通俗」？ |

SFT 有一个前提：**你手里有标准答案**。但很多场景下没有唯一正确答案——委婉的拒信和冷漠的拒信格式都对，但人更喜欢委婉的。

> **SFT 的局限**：它能教模型「照着你给的答案做」，但教不了模型「什么样的输出让人更满意」。

这就是 RLHF 要解决的问题。


### 7.3 RLHF：没有标准答案，但有好坏之分

RLHF = **Reinforcement Learning from Human Feedback**（基于人类反馈的强化学习）。

它的思路不是「给标准答案」，而是「给模型的行为打分」。

**RLHF 的三步走**：

```
第 1 步：让模型对同一个问题生成多个回答
         问题：「帮我写一封拒信」
         回答 A：「抱歉，你不能来。」（冷漠）
         回答 B：「很遗憾通知你…」（得体）
         回答 C：「感谢你的申请，但…」（温暖）

第 2 步：人类标注员给这些回答排序
         排序：C > B > A（C 最好，A 最差）

第 3 步：用排序数据训练一个「奖励模型」（Reward Model）
         奖励模型学会了预测「人会觉得这个回答打几分」
         
         然后用强化学习让模型去讨好奖励模型——
         「输出被打高分的东西，避免被打低分的东西」
```

> **SFT 教你「怎么做对」，RLHF 教你「怎么做让人满意」。**

SFT 和 RLHF 不是二选一的关系——**它们是先后顺序**：先 SFT 让模型「会做」，再 RLHF 让模型「做好」。


### 7.4 SFT vs RLHF：一张表说清

| 维度 | **SFT** | **RLHF** |
| :--- | :--- | :--- |
| **全称** | Supervised Fine-Tuning | Reinforcement Learning from Human Feedback |
| **数据** | 「输入 → 正确答案」的对子 | 人类对多个回答的排序 |
| **训练方式** | 和预训练一样（前向 → 算 Loss → 反向传播） | 强化学习（最大化奖励模型的打分） |
| **解决的问题** | 模型不会按你的格式/风格输出 | 模型的输出让人不舒服、不自然 |
| **需要标准答案？** | ✅ 需要 | ❌ 不需要，只需要「谁好谁坏」 |
| **成本** | 低（几百到几千条数据） | 高（需要人类标注员持续打分） |
| **你的笔记里** | 第 5-6 章就是 SFT | 暂未涉及 |

### 7.5 一张图看懂 ChatGPT 是怎么训出来的

真实的 ChatGPT 训练管线就是 SFT + RLHF 的组合：

```
预训练模型（GPT-3.5 / GPT-4 基座）
    │      读完互联网上的海量文本，学会了「语言本身」
    │
    ▼
阶段 1：SFT（监督微调）
    │      用人类写的「高质量对话」做训练数据
    │      模型学会：「用户这样问，我应该这样答」
    │      此时的模型已经能对话了，但回答可能很生硬
    │
    ▼
阶段 2：RLHF（人类反馈强化学习）
    │      人类标注员给模型的多个回答打分/排序
    │      模型学会：「不只答对，还要让人喜欢」
    │      这就是为什么 ChatGPT 聊起来很自然
    │
    ▼
ChatGPT（你正在用的产品）
```

> **ChatGPT 的「魔力」来自 RLHF。** SFT 让它会回答问题，RLHF 让它回答得让你舒服。

### 7.6 LoRA 在这张图里的位置

你可能注意到了：前面一直在说 SFT 和 RLHF，那 LoRA 呢？

**LoRA 不是第三种训练目标，而是一种训练手段。** SFT 和 RLHF 都可以用 LoRA 来做：

| | 用全量微调做 | 用 LoRA 做 |
| :--- | :--- | :--- |
| **SFT** | 显存 60–80 GB，1–3 天 | 显存 12–16 GB，2–6 小时 |
| **RLHF** | 几乎不现实（太贵，且需要同时训多个模型） | 可行，显存门槛大幅降低 |

> **你在第 6 章做的事，准确叫法是「用 LoRA 做 SFT」**——这是业界最主流的组合，也是你作为个人开发者最可能实际用到的微调方式。

### 7.7 延伸：你还可能听到这些名词

读完这一章，如果你去看开源模型的说明，可能会见到这些术语——它们都属于 SFT 范畴的不同叫法：

| 术语 | 全称 | 其实就是 |
| :--- | :--- | :--- |
| **Instruction Tuning** | 指令微调 | SFT 的一种，训练数据全是「指令 → 执行」格式 |
| **Chat Tuning** | 对话微调 | SFT 的一种，训练数据是多轮对话 |
| **DPO** | Direct Preference Optimization | RLHF 的简化版，不需要训奖励模型，直接拿排序数据做 SFT |

> 你不需要现在就全部记住。只需要知道：**它们都是 SFT 或 RLHF 的变体，而 LoRA 是你能用最低成本去实践它们的手段。**

### 二、Hugging Face 认证问题与解决

#### 2.1 问题现象

运行训练脚本时出现 `401 Unauthorized` 或 `404 Not Found` 错误，无法下载模型 `Qwen/Qwen2.5-0.5B-Instruct`。

#### 2.2 错误原因

按提示在浏览器中打开 `https://hf.co/oauth/device` 并输入设备码完成授权。

**第二步：使用正确的模型名称**

脚本参数应为 `--model-name Qwen/Qwen2.5-0.5B-Instruct`（注意是 `--model-name 而非 --model_name`）

## 9. 微调实战进阶：四个高频问题

第 8 章你跑通了 MiniLoRA，但真实项目里「训练完」只是开始。这一章补四个面试高频、但前面没展开的实战问题。

### 9.1 怎么评估微调效果？

微调完，你怎么知道模型真的「变好」了？四个层次，从客观到主观：

| 层次 | 怎么做 | 适合判断 |
| :--- | :--- | :--- |
| **测试集指标** | 留一部分数据不参与训练，训完用它测 Loss / 准确率 | 客观的「学没学会」 |
| **A/B 对比** | 同一个问题，微调前 vs 微调后各答一遍，对比输出 | 格式 / 风格是否变了 |
| **人工评估** | 抽样人工打分 | 主观的「好不好」 |
| **泛化测试** | 用训练数据之外的新场景测 | 是否过拟合 |

> 你的 MiniLoRA 实战用的就是「A/B 对比 + 人工检查格式」：同一个医疗问题，原版 Qwen 和 LoRA 版各答一遍，看格式有没有变成「三段式」。

### 9.2 怎么防过拟合？

过拟合 = 模型把训练数据「死记硬背」了，换新数据就露馅。

正则化的本质：**给损失函数加惩罚项，逼模型别「死记硬背」**。四种常见手段：

| 方法 | 怎么做 | 一句话 |
| :--- | :--- | :--- |
| **Dropout** | 训练时随机丢弃部分神经元 | 别依赖某一条路径（LoRA 里就是 `lora_dropout`） |
| **权重衰减（L2）** | 惩罚权重太大 | 逼模型用更简单的表达 |
| **早停（Early Stopping）** | 验证集 Loss 不再降就停 | 别训过头 |
| **更多数据 / 数据增强** | 给模型看更多变化 | 治本，但成本高 |

> 注意和 3.3 的「防灾难性遗忘」区分：防遗忘是怕模型**忘旧知识**（用 EWC 摁住重要权重），防过拟合是怕模型**死记新数据**（用 Dropout / 权重衰减 / 早停）。一个是「别忘」，一个是「别背」。

### 9.3 为什么需要混合精度训练？

混合精度 = 训练时同时用 **FP16（快但糙）** 和 **FP32（慢但准）**。

必要性就两条：

1. **省显存**：FP16 每参数 2 字节，FP32 是 4 字节——权重、梯度、激活全部减半。
2. **加速**：GPU 的 Tensor Core 对 FP16 计算有专门加速，比 FP32 快好几倍。

那「混合」在哪？——**权重用 FP16 存（省显存、算得快），梯度累加用 FP32（防精度损失导致训练发散）**。因为 FP16 只有约 3 位十进制有效数字，梯度累加时小数容易被「吞掉」，所以累加器要用 FP32 兜底。

代码里 `fp16=True` 或 `torch_dtype=torch.bfloat16` 就是开启混合精度。

> 一句话：FP16 负责「快」，FP32 负责「稳」，各取所长。

### 9.4 怎么解决输出重复和幻觉？

微调后两个典型毛病：

- **重复**：一句话反复说（「我是 AI 助手，我是 AI 助手……」）
- **幻觉**：一本正经编造不存在的东西（「根据 XX 医院……」，其实没有）

微调层面四条对策：

| 问题 | 对策 |
| :--- | :--- |
| 重复 | 推理时设 `repetition_penalty`（重复惩罚）+ 调低 `temperature` |
| 幻觉 | 数据质量把关——训练数据里别放编造的答案 |
| 两者通用 | 训练数据固定输出模板（如「建议→警示→就医」三段式），减少自由发挥 |
| 知识类幻觉 | 交给 RAG 实时检索，微调只管格式 / 风格，别让它「记知识」 |

> 核心：微调是教「行为」（格式、风格、语气），不是教「知识」。知识要更新的交给 RAG——微调硬记知识，记不住就幻觉。这正是 RAG vs 微调决策的核心。

## 10. 面试怎么讲

> "微调（Fine-tuning）是在预训练好的大模型上，用你自己的数据再训练一小段，把「你的规则」从外部 Prompt 变成模型的内部默认行为。它和预训练的差异就两点：数据量（几百~几千条 vs 海量）和成本（差几个数量级）。

> 全量微调贵在三点——显存（60-80GB）、时间（1-3 天）、灾难性遗忘。所以工程上主用 LoRA：冻结原模型权重，只训练旁路的 A×B 低秩小矩阵（参数量降到 0.1%-1%），用秩 r 控制参数量、lora_alpha 控制缩放。

> SFT 是喂「输入→标准答案」对（Alpaca 格式）让模型学会行为；RLHF 是让人打分训奖励模型、再用强化学习对齐偏好。核心是数据质量 > 数量。

> 我实战用 MiniLoRA（Qwen-7B + 医疗问答 + RTX 4090）跑通全流程，LoRA 适配器只有几 MB。"
