## 1. 为什么高并发需要缓存

核心矛盾：**读多写少 + 重复计算太贵**。

高并发场景下，绝大多数请求是「读」，而且大量请求问的是**同一个东西**（比如「宝宝发烧怎么办」这个问题一天被问 1000 次）。如果每次都去查数据库、都让 LLM 重新推理一遍，那是巨大的浪费。

**缓存就是「把算过/查过的结果存起来，下次直接用」**，从根上减少后端的压力——这是比限流更「治本」的削峰手段。

**类比**：餐厅后厨把热销菜提前炒好放保温箱（缓存），而不是每个客人点单后都从洗菜切菜开始现炒（每次现查库/现推理）。

> **前端视角**：缓存 ≈ 你天天在用的 `useMemo` / `memo`（算过的值别重算）、浏览器缓存、Service Worker。只不过后端缓存要考虑「多实例共享 + 一致性 + 过期」这些前端缓存不用太操心的东西。

## 2. 三个核心指标

| 指标 | 含义 | 目标 |
|:---|:---|:---|
| **命中率** | 命中缓存的请求 / 总请求 | 越高越好（>80% 才算有效） |
| **TTL** | 缓存的存活时间 | 平衡「新鲜度」和「命中率」 |
| **穿透率** | 没命中、打到后端的比例 | 越低越好 |

> 一句话：**命中率决定缓存有没有用，TTL 决定数据新不新鲜，穿透率决定后端还要扛多少。**

## 3. 多级缓存（L1 → L2 → L3）

真实系统不会只用一层缓存，而是「越近越快、越远越权威」的多层：

| 层级 | 是什么 | 速度 | 容量 | 特点 |
|:---|:---|:---|:---|:---|
| **L1 本地缓存** | 进程内存（Python dict / LRU） | 最快（纳秒） | 小（单机） | 单机私有，多实例不共享 |
| **L2 分布式缓存** | Redis | 快（毫秒） | 大 | 多实例共享，一致性好 |
| **L3 数据源** | 数据库 / 向量库 / LLM | 最慢 | 最大 | 最权威，最贵 |

**前端类比**：浏览器内存缓存（L1）→ Service Worker / CDN（L2）→ 源服务器（L3）。命中的层越靠前，用户越快、服务器越省。

> **为什么要有 L1？** Redis 再快也是网络调用（毫秒级）。真正的高频热点（比如「宝宝发烧怎么办」这种 Top 100 问题）放进进程内存，连网络都不走，快到极致。这就是你 baby-ai 成本控制里那个「100 条 LRU 缓存」干的事——它就是个 L1。

## 4. 三大经典问题（面试必问）

这是缓存最核心的考点。三个词都带「缓存」，但场景完全不同：

| 问题 | 触发场景 | 后果 | 解决方案 |
|:---|:---|:---|:---|
| **缓存穿透** | 查一个**根本不存在**的数据 | 缓存没数据，每次都打到 DB，恶意刷不存在的 id 能打穿 | 布隆过滤器 / 缓存空值 |
| **缓存击穿** | 一个**热点 key 过期的那一瞬间** | 海量并发同时打到 DB | 互斥锁重建 / 热点永不过期 / 逻辑过期 |
| **缓存雪崩** | **大量 key 同时过期**，或 Redis 整体宕机 | 全部请求瞬间压垮 DB | 过期时间加随机 / 多级缓存 / 集群高可用 |

### 4.1 缓存穿透（查不存在的数据）

**场景**：攻击者疯狂请求 `id=99999999` 这种数据库里根本没有的数据。缓存里没有，数据库里也没有，于是**每次请求都穿透缓存、直接打到数据库**。

**解决**：
1. **布隆过滤器（Bloom Filter）**：用一个内存数据结构提前判断「这个 key 一定不存在」，直接拦掉，不让它进 DB。
2. **缓存空值**：查不到也往缓存里存一个「空」标记（TTL 设短一点），下次同样的请求直接命中空标记，不再打 DB。

### 4.2 缓存击穿（热点 key 过期瞬间）

**场景**：某个 key 是超级热点（比如「宝宝发烧怎么办」），突然过期了。在它重建之前的那一瞬间，成千上万个请求同时 miss，全部砸到数据库/LLM。

**解决**：
1. **互斥锁重建**：只让**一个**请求去重建缓存，其他请求等待或先返回旧值（单飞/`singleflight` 思想）。
2. **热点 key 永不过期**：给热点 key 不设 TTL，用后台任务异步刷新。
3. **逻辑过期**：存两份——物理上不过期，但带一个「逻辑过期时间」，读时发现逻辑过期，返回旧值同时异步去刷。

> **前端类比**：击穿 ≈ 你的接口同时被 100 个组件调，每个都触发了一次请求——正确做法是「只发一个请求，其他共享这个 Promise 结果」（`singleflight` 就是干这个的）。

### 4.3 缓存雪崩（大量 key 同时过期 / Redis 宕机）

**场景**：假设 1 万个 key 都设了 60 秒 TTL，且是同一批创建的，那 60 秒后这 1 万个 key **同时过期**，缓存瞬间「清空」，所有请求集体砸向数据库。或者更糟——Redis 本身挂了。

**解决**：
1. **过期时间加随机值**：TTL 别设成整齐的 60 秒，而是 60~90 秒随机，让过期时间错开。
2. **多级缓存**：L1 本地缓存兜底，Redis 挂了本地还能顶一阵。
3. **Redis 集群 / 哨兵高可用**：缓存服务本身别单点。

> **一句话区分三个词**：穿透是「查不存在的数据」，击穿是「一个热点 key 过期」，雪崩是「一大片 key 同时过期 / 缓存挂了」。记忆口诀：**穿 = 假的、击 = 单点、崩 = 大面积**。

## 5. LLM 场景的缓存（结合你的项目）

LLM 应用比传统后端更「需要缓存」，因为**每次推理都烧钱烧 GPU**。能缓存的四类：

| 缓存对象 | 缓存什么 | 举例 |
|:---|:---|:---|
| **高频问答缓存** | 问题 → 标准答案 | 「宝宝发烧怎么办」→ 固定答案，命中直接返回，0 Token |
| **Embedding 缓存** | 文本 → 向量 | 同一段文档反复向量化很贵，缓存起来复用 |
| **检索结果缓存** | query → 检索到的文档 | 同一用户同一问题，直接复用检索结果 |
| **语义缓存（进阶）** | 语义相似的 query → 同一答案 | 用向量相似度判断「意思差不多」，命中同一答案 |

> 对应题库：工程落地 3.3 就是「同一用户同一问题的检索结果缓存 + 缓存过期与新知识更新的平衡」；4.12 是「LLM 结果、Embedding、检索结果的缓存设计」。

## 6. 缓存一致性（进阶，先有个概念）

缓存了数据，就要面对「缓存和数据库不一致」的问题。最常用的是 **Cache Aside（旁路缓存）** 模式：

> **读**：先查缓存 → 命中直接返回 → miss 则查 DB → 回填缓存。
> **写**：先更新 DB → **再删缓存**（不是更新缓存）。

关键点：**「更新 DB + 删缓存」而不是「更新 DB + 更新缓存」**，因为删缓存更简单、更不容易出现脏数据（下次读自然重建）。

## 7. 面试怎么讲

> "高并发削峰最治本的手段是缓存，核心是**多级缓存 + 防三大问题**。我按 L1 本地 LRU → L2 Redis → L3 数据源分层，热点的放 L1、共享的放 L2。三个坑要能防：**穿透**查不存在的数据，用布隆过滤器或缓存空值；**击穿**是热点 key 过期瞬间，用互斥锁重建；**雪崩**是大片 key 同时过期，给 TTL 加随机值错开。LLM 场景我重点缓存高频问答和 Embedding，命中一次就省一次推理成本。"
