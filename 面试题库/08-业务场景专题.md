## 题1：大模型应用中长期短期记忆机制的实现方法

**我的回答**：

记忆分两层，核心区别是「存哪、活多久」：

| 类型 | 存什么 | 存哪 | 生命周期 |
|:---|:---|:---|:---|
| **短期记忆** | 当前会话的上下文 | 服务端内存（dict / 会话对象） | 本次会话，重启/结束即丢 |
| **长期记忆** | 跨会话的用户画像、关键信息 | 向量库 / 数据库 | 持久化，下次会话复用 |

**长期记忆的实现流程**（以我项目为例，四步）：

```
对话结束 → LLM 提取关键信息（JSON：年龄/过敏史/关注点）
        → 存入 ChromaDB（user_profiles，session_id 做文档 ID，支持 upsert 合并）
        → 下次新会话：检索用户档案 → 转自然语言 → 注入 System Prompt
```

**两个关键细节**：

1. **提取用 temperature=0**：让 LLM 稳定输出结构化 JSON（`{baby_age, allergies, concerns}`），不随机。
2. **upsert 合并**：同一用户多次对话的信息自动合并，而不是每次新建一条。

**为什么要有长期记忆**：没有它，用户每次新会话都要重新自我介绍（「我宝宝 3 个月、牛奶过敏」），体验差；有了它，Agent 能跨多次对话记住用户情况，做个性化。

> **可补充的优化方向**：记忆衰减（太久没更新的档案降权重）、隐私脱敏、记忆容量管理。

**项目关联**：baby-ai 已实现——短期记忆 `session_manager.py`（内存 dict），长期记忆 `user_profile.py` + ChromaDB，提取信息注入 System Prompt。

**关键词**：短期记忆、长期记忆、跨会话记忆、ChromaDB、信息提取、System Prompt 注入、upsert、temperature=0

## 题7：超长模型上下文窗口限制的工程解决方案

**我的回答**：

**核心矛盾**：`内容总量 >> 上下文窗口容量`。所有方案只有两条路：**要么「减少塞进去的量」，要么「换个地方存」**。

五种方案：

| 方案 | 思路 | 代价 |
|:---|:---|:---|
| **① RAG 检索**（最主流） | 不全部塞，按需检索「最相关的 Top-K 段」塞进去 | 检索精度影响答案 |
| **② 上下文压缩/摘要** | 长对话/长文档先摘要成「关键信息」再塞 | 丢细节 |
| **③ 滑动窗口/截断** | 只保留最近 N 轮对话，更早的丢弃或摘要后保留 | 丢更早的信息 |
| **④ 分块 Map-Reduce** | 长文档切块→逐块摘要→合并总摘要 | 块之间丢上下文关联 |
| **⑤ 记忆分层** | 短期记忆进窗口，长期记忆存向量库按需检索 | 需要额外存储/检索 |

**重点展开 ④ Map-Reduce（长文档摘要的底层机制）**——模型没法一次读完超长文档，只能「分三步」：

```
① 分块：文档切成 N 块，每块都小于窗口
② Map：每块独立生成小摘要
③ Reduce：所有小摘要拼起来再摘要，得到总摘要
```

> 前端类比：Map-Reduce ≈ `arr.map(每块摘要).reduce(合并)`。另一种 Refine 策略是边读边更新累计摘要，串行但更连贯。

**我的项目里 ①②⑤ 都已落地**：RAG 混合检索解决「知识库 > 上下文」，跨会话长期记忆解决「历史 > 上下文」。

**项目关联**：RAG 检索 + 跨会话记忆已实现；可补长对话滑动窗口 + 摘要压缩、超长文档 Map-Reduce 总结。

**关键词**：上下文窗口、RAG 检索、上下文压缩、滑动窗口、Map-Reduce、Refine、长短期记忆、摘要

## 题11：大模型 API 响应延迟超 1 秒时的前端优化策略

**我的回答**：

第一个考点是**别拿传统前端套路套 LLM**——传统 API 几十毫秒一次性返回完整 JSON；LLM 是逐 token 串行生成，要几秒到几十秒，压缩/CDN/减请求数都治标不治本。

**核心思路一句话**：让用户「不用等完整结果」，要么边生成边看，要么先给替代品。

关键指标 **TTFT（首字延迟）**：从点发送到第一个字上屏的时间。用户对它极其敏感（超 1~2 秒就觉得卡），对后面吐字多久反而能接受。优化目标：**把 TTFT 压到 1 秒内**。

六种手段：

| 手段 | 做法 | 性质 |
|:---|:---|:---|
| **① 流式输出**（最核心） | SSE 逐 token 推，前端 `ReadableStream` 逐字渲染 | 治本，TTFT≈第一个 token 时间 |
| **② 感知性能** | 骨架屏 + 打字机 + 阶段提示（「检索中→思考中→生成中」） | 治标，让等待有反馈 |
| **③ 前端缓存** | 高频问题命中直接返回（SWR：秒回旧答案 + 后台刷新） | 0 延迟 |
| **④ 异步任务化** | >10s 任务改成「返回任务 ID → 轮询/SSE 通知 → 拉结果」 | 让用户先干别的 |
| **⑤ 请求管理** | 防重复提交 + `AbortController` 取消 + 「停止生成」按钮 | 防止用户行为放大延迟 |
| **⑥ 预取/预热** | 打字时预取、SSE 常连接、模型常驻内存 | 进阶 |

**⑤ 请求管理对 LLM 尤其重要**：取消/停止一个请求，还能省掉后面几十秒的 token 消耗。

**项目关联**：baby-ai 已实现 SSE 流式输出 + 打字机渲染；可补高频问答缓存（SWR）、停止生成按钮、异步任务化、TTFT 埋点。

**关键词**：TTFT、首字延迟、流式输出、SSE、ReadableStream、感知性能、骨架屏、SWR、异步任务化、AbortController、停止生成

## 题13：大模型上下文窗口扩展至 100 万 token 对现有业务场景的影响

**我的回答**：

窗口扩到 100 万 token，是不是 RAG/分块/摘要就都没用了？**答案是：依然需要，因为「装得下」≠「该全塞」。**

**好处**：

- 单次能塞进整本书/超长文档，不用分块、不用检索，直接全塞。
- 长对话几乎不丢上下文，不用滑动窗口。

**但带来三个新问题**：

| 问题 | 说明 |
|:---|:---|
| **成本暴涨** | 上下文每 token 都计费，塞 100 万 token 即使只问一句也极贵 |
| **延迟变高** | 上下文越长，prefill（处理输入）阶段越慢，TTFT 变高 |
| **Lost in the Middle** | 模型对「开头和结尾」记性好，对「中间」记性差，信息在中间易被忽略 |

**Lost in the Middle（迷失在中间）**——最容易被追问的点：

论文发现：把答案放在长上下文不同位置测模型能否找到，准确率呈 **U 型曲线**——放开头/结尾容易找到，放中间经常「看不见」。

> ⚠️「开头/结尾」是「相对位置」不是「字数硬边界」，且这个「谷」随上下文变长而**越深越宽**。

**工程启示**：① 关键信息（指令、问题、约束）别放中间，放开头或结尾；② 上下文不是越长越好；③ RAG 依然有价值——精准检索「最相关的几段」比「全塞」更能保证关键信息不被稀释。

**结论（面试关键句）**：即使窗口扩到 100 万，RAG 依然有价值——精准检索「最相关的几千字」比「把整本书全塞」更省、更快、更准。窗口变大不是「RAG 的终结」，而是「RAG 的边界放宽」：短文档可以直接全塞，超长内容还是要检索。

**项目关联**：baby-ai 的 RAG 检索就是「精准检索最相关几段」而非全塞，正好是 Lost in the Middle 的对策。

**关键词**：100 万 token、成本暴涨、TTFT、prefill、Lost in the Middle、U 型曲线、RAG 边界
