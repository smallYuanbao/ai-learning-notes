# LLM 接口延迟的前端优化（大模型 API 响应 > 1 秒）

> 📅 学习日期：2026-08-16
> 🔗 关联面试题：业务场景 & 架构设计专题 9.11（大模型 API 响应延迟超 1 秒时的前端优化策略）
> 🎯 前置：这是你前端老本行的题，但 LLM 的「慢」和传统接口的「慢」完全不一样——本篇专讲这个差异，以及对应的前端手段

---

## 1. 先认清问题：LLM 的「慢」和传统接口的「慢」不一样

这是这道题的第一个考点——**别拿传统前端的套路套 LLM**。

| 维度 | 传统 API | LLM API |
|:---|:---|:---|
| 延迟量级 | 几十 ms | 几秒 ~ 几十秒 |
| 返回方式 | 一次性返回完整 JSON | 一个字一个字「吐」出来 |
| 慢的原因 | 网络、数据库查询 | 推理本身就是**串行逐 token 生成** |
| 传统优化（压缩/CDN/减请求数） | 有效 | 治标不治本 |

> 所以 LLM 场景的前端优化核心只有一句话：**让用户不用「等完整结果」**。要么边生成边看，要么先给个替代品。

## 2. 核心指标：首字延迟 TTFT（Time To First Token）

TTFT = 从「用户点发送」到「第一个字出现在屏幕上」的时间。

**为什么它最关键**：用户对「多久看到第一个字」极其敏感（超过 1~2 秒就觉得卡），但对「后面吐字吐多久」反而能接受——因为看着它在打字，有反馈。

> 优化目标：**把 TTFT 压到 1 秒以内**。TTFT 达标了，哪怕整段回答要 20 秒，用户也不觉得慢。

## 3. 手段一：流式输出（最核心，治本）

**思路**：不等整段生成完，让模型「生成一个字就返回一个字」，前端逐字渲染。

- **协议**：SSE（Server-Sent Events）最常用——单向、轻量、天然按 chunk 推（对比 WebSocket 更省，详见 [流式输出优化.md](../04-工程化/流式输出优化.md)）。
- **前端**：`fetch` 配合 `ReadableStream` 逐块读取，或 `EventSource`。

**为什么治本**：同步方案要「等完整答案」才渲染，TTFT = 整段生成时间（可能 20 秒）；流式方案 TTFT ≈ 第一个 token 的生成时间（1 秒内），直接把最难受的「干等」干掉了。

## 4. 手段二：感知性能（治标，让等待不难熬）

流式还没回来之前，或非流式场景下，用「视觉反馈」填满空白：

| 手段 | 做法 | 作用 |
|:---|:---|:---|
| **骨架屏 / 加载态** | 先渲染一个「AI 正在输入」的占位 | 让用户知道「在动了」 |
| **打字机效果** | 流式天然自带逐字显现 | 看着在生成，等待变成「观赏」 |
| **阶段提示** | 「正在检索 → 正在思考 → 正在生成」 | 把一大段等待拆成有反馈的阶段 |

> 核心思想：**感知性能 ≈ 真实性能**。用户评价「快不快」很大程度是「等的时候有没有反馈」，而不是真的毫秒数。

## 5. 手段三：前端缓存（0 延迟）

**思路**：高频问题直接命中缓存，连请求都不发，延迟 = 0。

- **高频问答缓存**：Top 100 问题 → 固定答案，前端 `localStorage` / 后端缓存命中直接返回。
- **语义缓存**：语义相似的 query 命中同一答案（详见 [缓存设计.md](../04-工程化/缓存设计.md) §5）。

> 前端这一层能做的是「**上次问过一模一样的问题，先秒回旧答案，同时后台刷新**」——典型 SWR（stale-while-revalidate）思路，你前端熟。

## 6. 手段四：异步任务化（延迟 > 10 秒的场景）

**思路**：如果某些请求注定要很久（长文档总结、复杂 Agent 任务），别让用户干等，改成「任务模式」：

```
同步：发请求 → 一直等 → 等 30 秒 → 返回完整结果
异步：发请求 → 立刻返回「任务 ID」→ 前端轮询/SSE 通知 → 完成后拉结果
```

- 用户可以先干别的，结果好了再回来看。
- 对应工程化专项 4.8（异步 Agent 任务 > 10s 设计）。

## 7. 手段五：请求管理（防止雪上加霜）

延迟高的接口，最怕用户「狂点发送」制造更多慢请求。所以：

| 手段 | 做法 |
|:---|:---|
| **防重复提交** | 生成中禁用发送按钮（你熟的门槛就够用） |
| **取消上一次** | 用户改主意了，`AbortController` 取消上一个未完成的请求 |
| **停止生成** | 提供「停止」按钮——用户看够了就停，既省等待也省 token 成本 |

> 这三条本质是「**别让用户的行为放大延迟问题**」。取消 + 停止对 LLM 尤其重要，因为取消一个请求还能省掉后面几十秒的 token 消耗。

## 8. 手段六：预取 / 预热（进阶）

**思路**：在用户「还没问完」时就预判，提前准备。

- 用户正在打字时，根据前几个字预取可能的问题答案。
- 保持 SSE 连接常开，省掉每次建立连接的开销。
- 模型常驻内存（后端预热），减少冷启动。

> 这块偏进阶，面试点到「预取 + 连接复用」即可。

## 9. 面试怎么讲

> "LLM 接口的慢和传统接口不一样——传统是几十毫秒返回完整结果，LLM 是逐 token 生成、要几秒到几十秒，所以核心是把「等完整结果」变成「不等完整结果」。第一是流式输出，用 SSE 逐字推，把首字延迟 TTFT 压到 1 秒内，这是治本；第二是感知性能，骨架屏 + 打字机 + 阶段提示，让等待有反馈；第三是缓存，高频问题命中直接返回 0 延迟；超过 10 秒的改成异步任务化，先返回任务 ID 再通知结果。最后是请求管理——防重复、AbortController 取消、提供停止生成按钮，既防用户狂点放大延迟，也省 token。TTFT 是关键指标，它达标了用户就不觉得慢。"
