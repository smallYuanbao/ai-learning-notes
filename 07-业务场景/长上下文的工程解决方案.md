# 长上下文的工程解决方案（超长上下文窗口）

> 📅 学习日期：2026-08-16
> 🔗 关联面试题：业务场景 & 架构设计专题 9.7（超长上下文窗口限制的工程解决方案）、9.13（上下文窗口扩展至 100 万 token 的影响）
> 🎯 前置：接 RAG——RAG 本来就是「上下文装不下」时的主要解法，本篇系统梳理所有方案

---

## 1. 问题：上下文窗口有限，内容无限

LLM 的上下文窗口有硬上限（4K / 8K / 32K / 128K / 200K…），但用户想处理的内容（长文档、长对话、知识库）远超这个量。

**核心矛盾**：`内容总量 >> 上下文窗口容量`，怎么办？

所有方案的思路只有两条路：**要么「减少塞进去的量」，要么「换个地方存」**。

## 2. 方案一：RAG 检索（最主流）

**思路**：不把所有内容塞进上下文，而是**按需检索「最相关的几段」**塞进去。

- 用户提问 → 去向量库检索最相关的 Top-K 文档片段 → 只把这 K 段 + 问题塞进上下文。
- 效果：无论知识库多大（百万文档），塞进上下文的始终只有「最相关的几千字」。

> 这是「减少塞进去的量」的典型，你 [02-RAG全链路](../02-RAG全链路/) 里已经完整落地了混合检索 + Rerank + 意图路由，本质上都是在解决这个问题。

## 3. 方案二：上下文压缩 / 摘要

**思路**：长对话或长文档，先「摘要压缩」，只保留关键信息再塞。

- 长对话：把前面 10 轮对话摘要成一段「之前聊了什么」，替代原文。
- 长文档：**分块逐块摘要再合并**——模型没法一次读完超长文档，只能「分块读、逐块摘要、再合并」（具体机制见 §5）。

> 代价：摘要会丢细节，所以只适合「大意比细节重要」的场景。

## 4. 方案三：滑动窗口 / 截断

**思路**：只保留「最近 N 轮」对话，更早的丢弃或摘要后保留。

- 对话类应用最常用：窗口满了，把最老的对话挤出去。
- 进阶版：不是简单丢弃，而是「旧对话先摘要、再保留摘要」。

> 前端类比：滑动窗口 ≈ 你熟悉的「消息列表只渲染最近 N 条」，超出就虚拟滚动/丢弃，只是 LLM 这里是「上下文」而非 DOM。

## 5. 方案四：分块处理再合并（Map-Reduce）—— 长文档摘要的底层机制

**思路**：超长文档塞不进，就**切成小块、逐块处理、最后合并**。这也是 §3「长文档摘要」的具体实现——摘要不是「一次读完」，而是分三步：

```
① 分块：把文档切成 N 块，每块都小于上下文窗口
② Map：每块独立生成一个小摘要（逐块处理）
③ Reduce：把所有小摘要拼起来，再摘要一次，得到总摘要
```

**带数字的例子**（窗口 10 万字，文档 100 万字）：

```
100 万字 → 切 10 块（各 10 万，都能塞进窗口）
        → 每块摘要成 1 万字（得到 10 个共 10 万字摘要）
        → 拼起来再摘要 → 1 个总摘要（1 万字）✅
```

关键：**每一步喂给模型的都小于窗口**，模型从头到尾没「一次读完全文」，但拿到了全文摘要。

**文档巨长时递归多层**（摘要的摘要仍超窗口）：1000 万字 → 100 个 10 万块 → 100 个摘要 → 再分 10 组 → 10 个摘要 → 1 个总摘要，一层不够叠几层。

**另一种策略 Refine（边读边更新摘要）**：

| 策略 | 方式 | 特点 |
|:---|:---|:---|
| **Map-Reduce** | 每块独立摘要，最后合并 | 可并行、快，但块之间丢上下文关联 |
| **Refine** | 边读边用「累计摘要 + 当前块」更新 | 串行、慢，但保持全局连贯 |

> 适用：一本书总结、超长合同审阅这类「必须看全文」的任务。前端类比：Map-Reduce ≈ `arr.map(每块摘要).reduce(合并)`；Refine ≈ `reduce((累计, 块) => 摘要(累计 + 块))`。

## 6. 方案五：记忆分层（长短期记忆）

**思路**：把「上下文」拆成短期 + 长期两层，别什么都塞进当前窗口。

| 记忆类型 | 存什么 | 存哪 | 生命周期 |
|:---|:---|:---|:---|
| **短期记忆** | 当前对话的上下文 | 直接进上下文窗口 | 本次会话 |
| **长期记忆** | 跨会话的用户偏好、历史 | 向量库 / 数据库 | 持久化，下次用 |

> 这对应业务场景专题 9.1（长短期记忆机制），也对应你 [03-Agent开发/跨会话记忆.md](../03-Agent开发/跨会话记忆.md) 已经做的东西——长期记忆存向量库，每次只把「相关的记忆」检索进上下文，而不是全塞。

## 7. 上下文窗口变 100 万 token 了，还需要这些吗？（题 13）

这是题 13 的考点：窗口扩到 100 万 token，是不是 RAG / 分块 / 摘要就都没用了？**答案是：依然需要，因为「装得下」≠「该全塞」。**

**100 万 token 带来的好处**：

- 单次能塞进整本书 / 超长文档，不用分块、不用检索，直接全塞。
- 长对话几乎不丢上下文，不用滑动窗口。

**但带来了三个新问题**：

| 问题 | 说明 |
|:---|:---|
| **成本暴涨** | 上下文每 token 都计费，塞 100 万 token 即使只问一句也极贵 |
| **延迟变高** | 上下文越长，prefill（处理输入）阶段越慢，**首字延迟 TTFT 变高** |
| **Lost in the Middle** | 模型对「开头和结尾」记性好，对「中间」的信息记性差——信息在中间容易被忽略 |

**Lost in the Middle（迷失在中间）展开**——长上下文最容易被追问的一个点：

论文《Lost in the Middle》（2023）发现：把答案放在长上下文的**不同位置**测模型能不能找到，结果是——

```
准确率
 高 ┃ ╲                   ╱
    ┃   ╲               ╱
    ┃     ╲           ╱
 低 ┃       ╲_______╱    ← 中间最低
    ┗━━━━━━━━━━━━━━━━
     开头      中间     结尾
```

答案放**开头/结尾**容易找到，放**中间**经常被「看不见」，准确率呈 **U 型曲线**。

> ⚠️ **「开头/结尾」没有字数硬边界**——它是「在上下文里的相对位置」，不是「前 N 字/后 N 字」。论文是按位置比例（0%、10%…100%）测的，所以 4K 上下文和 100K 上下文的「开头」都指「最前面那一小段」。工程上大概把握：开头/结尾 ≈ 前后几百 ~ 一两千 token，中间 ≈ 其余一大片，越靠正中间越容易被忽略。而且这个「谷」会随上下文变长而**越深越宽**——上下文越长，中间丢得越多。

**为什么**：模型读上下文有「注意力偏好」——开头像锚点、结尾离要生成的下一个 token 最近，这两处天然受关注；中间被前后夹着、注意力被摊薄，容易被忽略。

**工程启示（面试要答的）**：

1. **关键信息别放中间**——指令、问题、关键约束放开头或结尾。
2. **上下文不是越长越好**——塞越多，中间越多，反而越容易被忽略。
3. **RAG 依然有价值**——精准检索「最相关的几段」比「全塞」更能保证关键信息不被稀释。

> **结论（面试关键句）**：即使窗口扩到 100 万 token，**RAG 依然有价值**——精准检索「最相关的几千字」比「把整本书全塞进去」更省、更快、更准。上下文窗口变大不是「RAG 的终结」，而是「RAG 的边界放宽」：以前必须检索，现在短文档可以直接全塞，但超长内容还是要检索。

## 8. 面试怎么讲

> "超长上下文的核心矛盾是内容总量远超窗口容量，解法两条路：要么减少塞进去的量，要么换个地方存。最主流是 RAG——按需检索最相关的几段塞进去，而不是全塞；其次上下文压缩、滑动窗口、分块 Map-Reduce、记忆分层（短期进窗口、长期存向量库）。就算上下文扩到 100 万 token，这些方案依然有价值，因为全塞有三个代价：成本暴涨、TTFT 变高、Lost in the Middle 中间信息被忽略。所以窗口变大只是放宽了 RAG 的边界，不是替代它。"
