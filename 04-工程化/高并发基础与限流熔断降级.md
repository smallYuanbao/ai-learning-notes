## 1. 什么是高并发、为什么要学

### 1.1 什么是高并发

**定义**：单位时间内，有大量请求同时（或几乎同时）到达系统。

衡量它的三个指标：

| 指标 | 全称 | 含义 |
|:---|:---|:---|
| **QPS** | Queries Per Second | 每秒处理的请求数 |
| **并发连接数** | Concurrent Connections | 同时保持的连接数量 |
| **TPS** | Transactions / Tokens Per Second | 每秒完成的事务数（LLM 场景常指每秒生成的 Token 数） |

> **高并发是「相对」的**，没有绝对数字。一个平时 10 QPS 的接口，活动瞬间冲到 1000 QPS——这 1000 就是高并发。判断标准不是「数字有多大」，而是「是不是超过了系统当前能扛的极限」。

**一个具体例子**：你的 AI 客服平时每秒 10 个用户提问，某天上了热搜，1 秒内涌进 1000 个提问。这 1000 个请求要同时经过「鉴权 → 意图识别 → RAG 检索 → LLM 推理」一整条链路——后端能不能扛住，就是高并发要解决的问题。

### 1.2 为什么你做前端时从没遇到过

这是你转型后第一个要补的认知差：

| | 前端 | 后端 |
|:---|:---|:---|
| 负责什么 | 发请求 + 渲染结果 | 接收并处理所有请求 |
| 并发发生在哪 | 不发生在你的 JS 里 | 发生在服务器上 |
| 用户量翻倍的影响 | 你的代码一行不用改 | 服务器压力直接翻倍 |

> **一句话**：你以前写的页面，不管 10 个人还是 100 万人访问，那份 JS 代码都一样——因为「扛住 100 万个请求」的活是后端干的，前端只干「渲染」这一份。所以高并发对前端是「盲区」，对后端 / AI 应用是「基本功」。空白，正常，现在补。

### 1.3 为什么要处理 / 学高并发

**不处理的后果（为什么「要处理」）**：

1. **系统崩溃**：请求堆积 → 内存 / 连接耗尽 → 服务宕机，甚至连锁拖垮整个系统（雪崩）。
2. **响应变慢**：请求排长队，用户等半天没结果。
3. **成本失控**：LLM 尤其——恶意刷量直接把 GPU 和 Token 账单打爆。
4. **体验崩坏**：又慢又崩，用户流失。

**为什么值得你学（为什么「要学」）**：

1. **面试高频**：AI 应用工程师方向，你题库 80 道工程落地题里一大半沾高并发。
2. **项目上生产**：baby-ai 要真正给别人用，就得面对真实并发量。
3. **LLM 服务更脆弱**：每个请求都吃 GPU、烧钱、还慢，比传统 Web 更依赖高并发手段。

## 2. 基础概念：三个词打地基

高并发的一切手段，都建立在三个基础概念上。这三个词不搞懂，后面全是悬空的。

### 2.1 并发 vs 并行

| | 并发（Concurrency） | 并行（Parallelism） |
|:---|:---|:---|
| 一句话 | **一个人**同时「交替」做多件事 | **多个人**同时「真正」做多件事 |
| 本质 | 任务被切成碎片，快速切换，看起来像同时 | 多个任务在多个 CPU 核心上真正同时跑 |
| 前提 | 单核也能做到 | 必须多核 |
| 前端类比 | JS 单线程 + 事件循环，一个线程「看起来」同时处理多个点击/请求 | 多个 Web Worker 真并行计算 |

> **关键认知**：高并发里的「并发」，绝大多数是「并发」不是「并行」——靠的是「切换」和「异步等待」，不是靠堆 CPU 核数。

### 2.2 同步 vs 异步

| | 同步（Sync） | 异步（Async） |
|:---|:---|:---|
| 一句话 | 排队等，做完才走 | 不等，先干别的，干完通知我 |
| 阻塞 | 阻塞当前执行流 | 不阻塞 |
| 前端类比 | `alert()`——不点掉，后面代码全卡住 | `fetch().then()` / `await`——请求发出去，继续跑别的 |

> **为什么高并发必须异步？** 一个 LLM 服务，90% 的时间在「等」——等模型推理、等网络返回、等数据库查询，而不是「算」。同步写法下，等待时 CPU 只能傻站着；异步写法下，等待时 CPU 立刻去处理下一个请求。**同样一台机器，异步能扛的并发量是同步的几十倍。**

### 2.3 进程 / 线程 / 协程

这是「并发到底靠什么实现」的三个层级，从重到轻：

| | 进程（Process） | 线程（Thread） | 协程（Coroutine） |
|:---|:---|:---|:---|
| 类比 | 独立的一整栋楼 | 楼里的多个房间（共享水电） | 房间里你快速切换做多件事 |
| 内存 | 独立，隔离 | 共享进程内存 | 共享线程内存 |
| 切换开销 | 大 | 中等 | 极小（用户态，无系统调用） |
| Python 实现 | `multiprocessing` | `threading`（受 GIL 限制） | `asyncio` / `async/await` |

> **前端视角一句话**：进程 = 多开几个浏览器窗口；线程 = 一个页面里的多个 Web Worker；协程 = JS 事件循环里那一堆 Promise / microtask，由一个主线程调度。

> **Python 的坑（GIL）**：CPython 有个全局解释器锁（GIL），导致**多线程跑 CPU 密集任务时并不能真并行**。但 GIL 不影响 I/O 等待——所以 Python 做高并发的正确姿势是**协程（asyncio）+ 异步框架**，而不是多线程。这就是为什么 FastAPI 用 `async def` 就能高并发。

**FastAPI 为什么天生高并发**：它底层是 asyncio + 协程。每个请求进来，`await` 一挂起，事件循环立刻切去处理下一个请求，一个进程就能同时扛几千个「在等待」的连接。

## 3. 高并发三件套——限流 / 熔断 / 降级

搞懂了「并发靠异步」，接下来是保护后端的三个手段。核心问题只有一个：

> **请求像洪水一样涌进来，后端资源有限，怎么保证不崩？**

三件套各管一段：

- **限流**：管「进」——让多少请求进来
- **熔断**：管「依赖」——下游挂了，别被它拖死
- **降级**：管「体验」——资源不够，牺牲次要保核心

### 3.1 限流（Rate Limiting）——控制「进来多少」

**定义**：限制单位时间内的请求数量，超过就拒绝或排队。

**类比**：银行取号机。大厅一次只能进 50 人，第 51 个人必须在门外等。这样柜台（后端）永远不会被挤爆。

**常用算法**（四种，从简单到常用）：

**① 固定窗口（Fixed Window）**

- **思路**：把时间切成固定窗口（如 1 秒），每窗口一个计数器，超过 N 拒绝，窗口结束归零。
- **例子**（限「1 秒最多 10 个」）：0.0~1.0 秒计数器从 0 累加，到 10 就拒第 11 个；1.0 秒归零，下一窗口重新算 10 个名额。
- **坑**：窗口边界「双倍突发」——0.9 秒来满 10 个 + 1.0~1.1 秒又放 10 个，0.2 秒内实际放行 20 个（限额的 2 倍）。
- **前端类比**：最朴素的计数器。

**② 滑动窗口（Sliding Window）**

- **思路**：不按整秒切，永远看「最近 1 秒」这个滑动区间，记录每个请求时间戳，统计区间内数量。
- **例子**（限「最近 1 秒最多 10 个」）：任意时刻 t，数 `[t-1秒, t]` 内请求数，已有 10 个就拒绝新请求。
- **特点**：窗口连续滑动，不会在边界突然归零，消除了双倍突发，更平滑。代价是存时间戳、稍复杂。
- **前端类比**：带时间戳的计数器——统计「最近 1 秒点了多少次」，而不是「这一秒点了多少次」。

**③ 令牌桶（Token Bucket）★ 最常用**

- **思路**：一个容量固定的桶，系统以固定速率往里放令牌（如每秒 10 个），桶满丢多余令牌；每个请求要先「拿走一个令牌」才能通过，桶空就拒绝。
- **例子**（容量 10，每秒放 10 个）：桶初始满，突发 10 个请求各拿一个令牌全通过（桶空，这就是「允许突发」）；第 11 个无令牌可拿被拒；1 秒后补 10 个令牌又能放 10 个。
- **特点**：允许突发、又限平均速率——有存货能一波放走，长期不超放令牌速率。最灵活，生产首选（Redis + 令牌桶、Guava RateLimiter 都是它）。
- **前端类比**：额度池——攒够额度能连续操作，用完等慢慢回血。

**④ 漏桶（Leaky Bucket）**

- **思路**：请求像水倒进有洞的桶，洞固定大小，请求以固定速率流出（被处理），桶满多余直接溢出丢弃。
- **例子**（容量 10，漏速每秒 10 个）：突然涌进 100 个，桶只能装 10 个，后 90 个直接溢出丢弃；桶里 10 个按每秒 10 个的固定节奏处理。
- **特点**：绝对匀速，不管进来多猛出去都是固定速率；代价是突发流量被丢 / 被憋，不像令牌桶灵活。
- **前端类比**：固定帧率的节流——不管事件多频繁，处理永远固定节奏，多余直接丢。

**一张表收口**：

| 算法 | 核心机制 | 前端类比 | 一句话 |
|:---|:---|:---|:---|
| 固定窗口 | 每 N 秒归零的计数器 | 简单计数器 | 每 1 秒数一遍，超了拒绝 |
| 滑动窗口 | 永远看「最近 N 秒」 | 带时间戳的计数器 | 窗口连续滑动，无边界突变 |
| 令牌桶 | 固定速率放令牌，请求抢令牌 | 额度池 | 有存货就放，能吸收突发 |
| 漏桶 | 固定速率流出，桶满溢出 | 固定帧率节流 | 绝对匀速，突发直接丢 |

> **记忆口诀**：固定窗口有「双倍突发」、滑动窗口「平滑」、令牌桶「能突发 + 限均值」（首选）、漏桶「绝对匀速」。

> **前端类比**：限流 ≈ 你写过的「节流 throttle」——同一个操作，规定时间内只真正执行一次，多余的丢弃。令牌桶则更像「防抖 + 允许一定次数的突发」。

**LLM 场景为什么尤其需要限流**：LLM 是重资源（每次推理都要吃 GPU）。一个恶意用户狂刷 1000 次，能把你的 GPU 和 Token 账单打爆。限流既是「防过载」，也是「控成本」（对应 工程落地 4.5）。

**算法之外：限流落地还要考虑这 6 个维度**

四种算法只解决「怎么数流量」，真正落地还要决定「按谁限、在哪限、限多严、限完怎么办」：

**① 按谁限（限流维度，可多层叠加）**

| 维度 | 例子 |
|:---|:---|
| 按 IP | 每个 IP 每分钟 60 次 |
| 按用户 | 普通用户 20 次/分，VIP 100 次/分 |
| 按 Token / API Key | 每个 key 每天 1 万次 |
| 按接口 | 生成接口 10 次/分，查询接口 100 次/分 |
| 按全局 | 总 QPS 不超过 1000 |

> 通常「全局总闸 + 每个用户/接口的细闸」叠加：就像公司有「整栋楼容量上限」，也有「每人办公位」「每部门预算」。

**② 在哪限（限流位置）**

| 层次 | 位置 | 特点 |
|:---|:---|:---|
| 网关层 | Nginx / 网关 / 负载均衡 | 最外层拦截，省资源 |
| 应用层 | 中间件（slowapi）/ 装饰器 | 灵活，能按业务细控 |
| 业务层 | 某接口内单独判断 | 只限最贵的那个操作 |

> 越靠外越「一刀切」但越省资源；越靠里越灵活但已消耗部分计算。生产上常「网关层粗限 + 应用层细限」。

**③ 限多严（时间粒度，多重配额）**

秒级（防突发）+ 分钟级（防持续）+ 天级（防总量），多尺度叠加。防止「第 59 秒打满、第 1 秒再打满」的时间差——只看分钟级，有人能在 2 秒内打出瞬时 2 倍流量。

**④ 限完怎么办（超限策略）**

| 策略 | 做法 |
|:---|:---|
| 直接拒绝 | 返回 429「请求太频繁」 |
| 排队等待 | 进队列慢慢处理（漏桶思想） |
| 降级 | 给缓存结果而不是实时推理 |
| 人机验证 | 弹验证码确认非机器人 |

**⑤ 单机 vs 分布式（多实例的坑）**

单机限流的令牌桶存在单进程内存里，多实例部署时各自独立，实际总流量 = 单机限制 × 实例数。要真控住总量，得把桶/计数器放 **Redis**，所有实例共享，靠原子操作（INCR / Lua 脚本）保证并发安全。

> 前端类比：单机限流像「每个窗口各自发号」，分布式像「所有人排同一台取号机」——后者才能真把总人数控住。

**⑥ LLM 场景：按 Token 限，不按请求次数**

一次请求可能烧 100 token，也可能烧 10000 token（长上下文）。按「次数」限流，有人一次请求就能打爆 token 账单。所以对外提供 LLM API，配额应是「每分钟 X token」而非「每分钟 X 次」。

> **一句话**：限流 = 算法（怎么数）× 维度（按谁限）× 位置（在哪限）× 粒度（限多严）× 策略（怎么办）× 单机/分布式（多实例怎么办），LLM 场景再把「次数」换成「token」。

### 3.2 熔断（Circuit Breaking）——控制「失败蔓延」

**定义**：当下游服务连续失败达到阈值，直接「断开」不再调用它，快速失败；过一段时间再试探性恢复。它的本质是**保护上游自己**，别被一个挂掉的下游拖垮。

**核心：三态状态机**（抓住这三个状态就抓住了熔断的本质）

| 状态 | 含义 | 行为 |
|:---|:---|:---|
| **Closed（关闭）** | 正常 | 正常调用下游 |
| **Open（打开/熔断）** | 下游连续失败 N 次 | **不再调用**，直接返回失败，快速失败 |
| **Half-Open（半开）** | 试探期 | 放行少量请求试探，成功就回 Closed，失败继续 Open |

**四个关键参数**（面试问「熔断怎么配置」就答这几个）：

| 参数 | 含义 | 常见值 |
|:---|:---|:---|
| **失败阈值 N** | 连续失败多少次触发熔断 | 5 次 |
| **熔断时长** | Open 持续多久后进入 Half-Open | 30 秒 |
| **试探请求数** | Half-Open 时放行几个请求去试探 | 1~3 个 |
| **失败率阈值** | 另一种触发方式：时间窗口内失败率超过多少 | 50% |

**什么算「失败」**（触发条件，不能只看抛异常）：

1. **超时**：下游超过 N 秒没响应（最常见，比如 LLM 推理 10 秒没回）
2. **返回错误**：下游返回 5xx 状态码 / 错误码
3. **抛异常**：连接拒绝、连接超时等网络异常

> ⚠️ 注意：**熔断只管「连下游都连不通 / 都失败」**。如果只是「这次返回的质量差一点」（比如 LLM 回答得不够好），那不算失败、不该熔断——那是「降级 / 重试」的范畴。

**一个完整例子**（带数字，跟着走一遍）：

假设你的 AI 应用调用 DeepSeek 主模型：

```
t=0s   状态 = Closed（正常），每个请求都能拿到回复
t=1s   下游开始抽风，请求连续超时
       ┌─ 第 1 个超时、第 2 个超时、…、第 5 个超时
       ↓
t=2s   连续失败达到阈值 5 次 → 状态变为 Open（熔断）
       熔断期间（30 秒内）：所有请求【不调下游了】，
       直接快速失败，返回「服务繁忙，请稍后再试」
t=32s  熔断时长到了 → 状态变为 Half-Open
       只放行 1 个请求去试探下游
       ├─ 成功 → 状态回到 Closed，恢复正常（熔断解除）
       └─ 失败 → 重新 Open，再熔断 30 秒（甚至翻倍，指数退避）
```

关键点在 **t=2s 到 t=32s 这 30 秒**：如果没熔断，这 30 秒里成千上万个请求会一个接一个「傻等 10 秒超时」，占满连接池，把上游拖垮。有了熔断，它们**立刻失败**，上游稳如泰山。

**两种触发方式**：

| 方式 | 逻辑 | 适用 |
|:---|:---|:---|
| **计数熔断** | 连续失败 N 次就熔断 | 简单直观，适合「下游彻底挂了」 |
| **比例熔断** | 滑动窗口内失败率 > 50% 就熔断 | 更精细，适合「下游时好时坏」 |

**熔断 vs 重试 vs 降级（别搞混）**：

| 手段 | 动作 | 一句话 |
|:---|:---|:---|
| **重试** | 失败了再试几次 | 「再试一次，也许好了」 |
| **熔断** | 失败太多，别再调了 | 「别再调了，歇会儿」 |
| **降级** | 调不了，换个兜底 | 「调不了就换个笨办法」 |

三者通常是**组合拳**：先**重试** 2 次 → 还失败 → **熔断**（不再调主模型）→ 熔断期间用**降级**（切备用小模型）兜底。

**类比**：家里保险丝。电路短路了，保险丝「啪」一声先断电，避免把整栋楼烧了；过一会儿你合闸试探，正常了就恢复供电。

> **前端类比**：请求连续超时后，你不再无脑重试，而是先给用户一个「稍后再试」的提示，过几秒再悄悄试一次——这就是手动版熔断。对应的几个参数：连续超时 N 次（失败阈值）、「过几秒再试」（熔断时长）、「悄悄试一次」（Half-Open 试探）。

**为什么需要熔断**：如果没有熔断，下游一个服务挂了，上游每个请求都傻等它超时（比如等 30 秒），大量请求堆积、占满连接池，最后**上游自己也被拖垮**——这就是「雪崩」。熔断就是那个「快速失败」，切断雪崩链。

> 💡 **和限流的区别**：限流是「请求太多，我拒一部分进来」；熔断是「下游挂了，我干脆不调它」。一个是管「进」，一个是管「出」。三件套里，限流在「入口」，熔断在「出口（调下游）」，降级是「兜底」。

> **LLM 场景的熔断**：主模型（DeepSeek）连续超时 → 熔断主模型 → 半开试探 → 还不行就切备用小模型（这是降级）。这正是你项目里「三级降级」该干的事。传统后端熔断的可能是「数据库连接」，你的应用熔断的是「模型 API 调用」，本质一模一样。

### 3.3 降级（Degradation / Fallback）——控制「服务质量」

**定义**：资源不够或依赖挂了时，主动牺牲次要功能，保住核心功能可用。它的本质是**保证用户「至少拿到一个可用结果」，而不是整个服务崩掉**。

**核心原则：保核心、弃次要、永远有兜底**（一句话记住降级的灵魂）。

**降级降什么？四个常见维度**（面试问「降级怎么设计」就答这几个）：

| 维度 | 做法 | 例子 |
|:---|:---|:---|
| **服务降级** | 主服务挂了切备用 | DeepSeek 挂了切备用小模型 |
| **功能降级** | 关掉次要功能保核心 | 高峰期关掉「历史对话推荐」，只留问答 |
| **数据降级** | 实时数据换成缓存/旧数据 | 检索超时改返回缓存的旧结果 |
| **性能降级** | 用更慢但能用的方案 | 关掉 Rerank 只做粗排，慢点但能出结果 |

**「降级」和「崩溃」的边界（底线）**：降级后用户**还能用、还能拿到结果**（只是慢一点/差一点）；崩溃是用户直接什么都拿不到。降级的底线就是——**永远别让用户空手而归**。

**什么时候触发降级（触发时机）**：

1. **依赖超时 / 失败**：下游挂了或响应超时（最常见）
2. **熔断触发后**：熔断把主依赖切断了，必须降级兜底（熔断和降级是搭档）
3. **资源告警**：CPU / 内存 / 连接池逼近上限
4. **主动降级**：大促 / 高峰前，主动先关次要功能保核心

**一个完整例子：主模型挂了怎么「逐级降级」**（这就是你 baby-ai 三级降级干的事）：

```
第 1 级：正常 → 主模型（DeepSeek）+ RAG 检索，给最好答案
        ↓ 主模型挂了 / 超时
第 2 级：降级 → 切备用小模型，先保证有回复（质量差一点）
        ↓ 连备用模型也挂了
第 3 级：再降级 → 返回兜底通用回答 / 缓存答案
                （比如「抱歉，稍后再试」+ 历史常见问题）
```

> 关键：**每一级都比上一级「差一点但更稳」**，逐级往下退，直到退到一个「绝对能兜住」的底线。降级要有「预案」，不是出错了才手忙脚乱。

**LLM 场景的典型降级**：

| 场景 | 降级策略 |
|:---|:---|
| 主模型（DeepSeek）挂了 | 切换到备用小模型，先保证有回复 |
| RAG 检索超时 | 降级为纯 LLM 回答（不带检索） |
| 检索不到相关文档 | 返回兜底通用回答，而不是「我不知道」 |
| 图片/附件服务挂了 | 返回文字 + 占位图 |
| Rerank 服务挂了 | 跳过重排，直接用初排结果 |

> **前端类比**：图片加载失败时，你给「占位图 + 文字说明」而不是整页白屏；接口挂了时，给「加载失败，点击重试」而不是让页面卡死——这就是前端一直在做的降级。后端降级是同一套思想，只是范围更大、要提前写预案。

**类比**：春运买不到高铁票，就降级坐绿皮车——慢一点、差一点，但「能到」。

**降级 vs 熔断 vs 限流（三件套关系）**：

| 手段 | 管什么 | 触发时机 | 效果 |
|:---|:---|:---|:---|
| **限流** | 进（请求量） | 请求超过阈值 | 拒掉多余请求 |
| **熔断** | 依赖（下游服务） | 下游连续失败 | 不再调用下游 |
| **降级** | 体验（服务质量） | 依赖不可用 / 资源不足 | 换个方案兜底 |

三者是**递进配合**：限流挡洪峰 → 进来的请求发现下游挂了就熔断 → 熔断期间用降级兜底，保证「不崩 + 有响应」。

> **关键**：降级是「主动」的、有预案的，不是「出错后被动崩溃」。核心原则——**保核心功能，弃次要功能，永远让用户至少拿到一个可用结果**。

### 3.4 三件套一句话对比

| 手段 | 管什么 | 解决什么问题 | 类比 |
|:---|:---|:---|:---|
| **限流** | 进（请求量） | 请求太多，后端过载 | 取号机控制进大厅人数 |
| **熔断** | 依赖（下游服务） | 下游挂了，失败蔓延成雪崩 | 保险丝短路断电 |
| **降级** | 体验（服务质量） | 资源不足，保不住全量 | 高铁票→绿皮车 |

三者常**组合使用**：限流挡住洪峰 → 没挡住的请求进来，发现下游挂了就熔断 → 熔断期间用降级兜底，保证「不崩 + 有响应」。
