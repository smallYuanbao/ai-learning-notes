# vLLM原理与选型

> 📅 学习日期：2026-07-31
> 🔗 关联面试题：工程化专题 模型部署/高并发相关题目

vLLM 是一个专门为大型语言模型设计的高吞吐量、内存高效的推理和服务引擎。

**vLLM 是什么？简单来说就是 用来本地私有化部署大模型的工具，它相比于传统的HuggingFace更快、更省钱。**

## 1. 核心思想

**核心思想：用操作系统的思路管理显存**

vLLM 高性能的核心，在于它革命性的显存管理方式。你可以把它想象成一个极其高效的“显存管家”。

在传统LLM服务中，为每个请求分配的显存是连续且保留的，这会导致两个问题：

1. **显存浪费**：就像你租了一整间仓库，但只用了其中一个角落，剩余空间被浪费了。

2. **难以共享**：即使两个请求有相同的开头（例如相同的提示词），也无法共享这部分已计算的缓存，导致重复计算。


vLLM 的核心思想是借鉴操作系统的**虚拟内存和分页**概念，发明了 **pagedAttention** 技术。

### 1.1 虚拟内存分页管理

**概念**：指操作系统和CPU配合实现的内存虚拟化管理技术。它是当前主流的虚拟内存实现方案，承担着虚拟地址到物理地址的映射、内存按需分配与交换的核心功能。

**定义**：将虚拟地址空间和物理内存空间划分为大小固定的标准单元（通常为4KB），分别称为“页”和“页框”，操作系统通过页表记录虚拟页到物理页框的映射关系，实现虚拟地址到物理地址的转换，并在物理内存不足时，将不常用的内存页交换到硬盘存储，需要时再重新加载回物理内存。

这是理解“分页管理”最形象的例子：

| 场景 | 传统方式（无分页/连续分配） | 分页管理方式（有分页） |
|------|------|------|
| 存放地点 | 一张超长大桌子（物理内存），整本书必须完整连续放上去才能看 | 活页笔记本（虚拟内存），桌上只放正在看的几页，其余拆散塞书柜（硬盘） |
| 查找方式 | 找第 100 页必须从书开头数起（连续地址），桌面有咖啡杯（碎片）就放不下 | 每页有页码（虚拟地址），页表瞬间定位”第 100 页在桌面左上角，第 101 页在书柜” |
| 结果 | 桌面利用率极低，碎片一多书就看不了（OOM） | 能塞一页算一页，不同书的散页可以摆满桌面，利用率极高 |


**三大核心**

- 虚拟地址：程序（比如你的 Python Agent 代码）以为自己在操作的内存地址（比如从 0x000 到 0xFFF，看起来是连续的）。

- 物理地址：真实的显卡（GPU）或内存条（RAM）上的实际存储位置。

- 页表（Page Table）：操作系统的“翻译官”。它记录着“虚拟地址的第 X 页，对应物理内存/硬盘上的第 Y 块”。



## 2. pagedAttention（vLLM 的基石）

工作原理如下：

1. **分块管理**：将每个请求的KV缓存（即模型在生产过程中产生的关键中间数据）划分为一个个固定大小的KV块（KV Blocks）。

2. **非连续存储**：这些KV 块不需要存储在显存的连续空间中，而是可以分散地存放在任何有空位的地方。

3. **按需分配**：模型在生成时，需要多少显存就动态分配多少个块，彻底消除了传统方式下的显存碎片和浪费。

> KV缓存（Key-Value Cache）是 Transformer模型在生成文本时，为了不重复计算前面所有token的注意力而保存下来的中间状态。它是 LLM 中最消耗显存的部分之一。



## 3. 核心工作流程

vLLM的工作流程围绕其核心组件LLMEngine展开：

1. 接收请求：LLMEngine 接收来自客户端的请求。

2. 输入处理与调度：引擎对请求进行处理，并通过一个智能调度器（Scheduler）决定接下来处理哪些请求。这是实现持续批处理的关键，它能在每个生成步骤动态地加入或移除请求，从而最大化GPU利用率。

3. 模型执行：调度好的批次被发送到模型进行推理。模型执行可能分布在多个GPU甚至多台机器上。

4. 输出处理：模型生成的输出（token）经过处理后返回给客户端。

## 4. vLLM 为什么快

vLLM 的高性能来自多个层面的协同优化，其中pagedAttention 是基础：

- **极致的内存效率**：通过PagedAttention ，vLLM 的显存利用率接近100%，允许在相同硬件上支持更大的模型、更长的上下文和更多的并发请求。

- **智能的批处理策略**：持续批处理确保了GPU始终在处理有用的工作，而不是空闲等待。

- **丰富的优化技术**：vLLM 集成了大量前沿的优化技术，包括：
    - 前缀缓存（Prefix Caching）：自动识别并缓存请求中重复的公共前缀（如系统提示词），新请求可直接复用，避免重复计算。

    - 分块预填充（Chunk Prefill）：将长输入提示词的预填充阶段分成小块，与解码阶段交错进行，提高整体吞吐。

    - 投机解码（Speculative Decoding）：使用一个快速的小模型“猜”大模型接下来会生成的多个token，如果猜对了，就能一次生成多个token，极大加速解码过程。

    - 量化与内核优化：支持FP8、INT8、GPTQ等多种量化技术来减小模型体积，并集成了FlashAttention等高效注意力内核来加速计算。

## 5. Ollama vs vLLM 对比

| 对比维度 | Ollama | vLLM |
|------|------|------|
| 核心定位 | 本地开发、实验和原型搭建 | 高性能、高并发的生产环境部署 |
| 设计目标 | 简单易用，追求”开箱即用” | 极致性能，追求最高吞吐量和最低延迟 |
| 并发能力 | 低并发表现良好，高并发下性能下降 | 为高并发而生，并发越高优势越明显 |
| 性能数据 | 高并发下吞吐量约 41 TPS | 高并发下可达 **793 TPS**（Ollama 的 19 倍） |
| 核心技术 | 基于 llama.cpp | 独创 **PagedAttention** 技术 |
| 硬件要求 | 亲民，消费级 GPU 甚至 CPU 可运行 | 依赖高性能 NVIDIA GPU |
| 易用性 | 极高，一行命令搞定 | 中等，需一定配置 |
| 模型支持 | 精选主流开源模型 | 广泛，与 HuggingFace 生态集成 |
| 适用场景 | 个人开发、本地学习、PoC | 生产级 AI 应用、高并发 API 服务 |
| 你的项目 | ✅ 当前使用 | 后续升级目标 |

**TPS：Tokens Per Second（每秒生成的Token数）。高并发下Ollama 每秒产出41个Token，vLLM能产出793个Token --- 差不多快 20 倍。**

### 5.1 TPS vs 响应时间（Latency）

| 指标 | 含义 | 谁关心 |
|------|------|------|
| TPS（吞吐量） | 系统每秒总共能生成多少个 Token | 后端/运维：服务器能不能扛住 |
| 响应时间（延迟） | 用户发完消息到看到第一个字的等待时间 | 用户：要等多久才有反应 |

### 5.2 为什么性能差那么多

- OLLAMA（基于llama.cpp）：采用的是相对传统的静态分配方式。也就是当一个请求进来，系统会预先为它划好”一块地“。这块地不能太大（浪费），也不能太小（不够用），灵活性较差。

- vLLM：采用的是创新 pagedAttention 技术，它能将显存像书页一样分成许多小块，按需动态分配。这种方式显存利用率极高，能同时处理大量请求，从而实现19倍于Ollama的吞吐量。



## 6. PagedAttention 的“分页”思想和操作系统的虚拟内存分页有什么异同

### 6.1 相同点

| 相似维度 | 操作系统（OS）虚拟内存 | PagedAttention（vLLM） | 核心目的 |
|------|------|------|------|
| 分块存储 | 物理内存（RAM）切成 4KB 固定页框 | 显存（VRAM）切成固定大小 KV 块 | 消除外部碎片，不要求内存连续 |
| 逻辑→物理映射 | 虚拟地址 → 页表 → 物理地址 | 逻辑位置（第 X 序列 Token Y）→ 块表 → 显存地址 | 让上层程序感觉存储是连续的 |
| 按需分配 | 程序申请 10GB，OS 先”画饼”，写入时才分配物理页 | 生成新 Token 时动态申请空 KV 块，不提前预留 | 避免”预先圈地”造成的巨大浪费 |
| 共享读 | 多进程映射同一份物理内存（共享库、mmap） | 多请求共享相同 Prompt（如 System Prompt），共用 KV 缓存块 | 节省重复计算和存储空间 |

### 6.2 不同点

| 差异维度 | 操作系统（OS）虚拟内存 | PagedAttention（vLLM） | 根本原因 |
|------|------|------|------|
| Swap 代价 | 慢但能忍：内存不够时脏页移到硬盘（毫秒级），普通程序只是”卡一下” | 快但绝不能忍：KV 块移到 CPU 内存需经 PCIe 总线，GPU 空转，吞吐断崖下跌 | GPU 是”饥饿的野兽”，绝不能等 CPU 喂数据 |
| Page Fault 处理 | OS 截停进程：缺页时 CPU 触发异常，OS 接管从硬盘读，进程暂停 | 软件显式管理：调度器提前预判，通过 CUDA 流异步预取 | LLM 推理 Token 按序产生，访存高度可预测，无需”紧急刹车” |
| 页表粒度 | 4KB ~ 2MB（硬件 MMU 固定） | 16~32 Token（约几十 KB），远大于 OS 4KB | 频繁查表消耗 GPU 算力，块太小导致块表过大 |
| 核心问题 | 解决”物理内存不够用”（容量不足） | 解决”显存碎片和低并发”（管理低效） | OS 面对随机访问，vLLM 面对有序注意力计算 |

## 7. Continuous Batching 怎么做到“随到随处理”

vLLM的实现逻辑：

| 步骤 | 调度器做的事 | 效果 |
|:---:|------|------|
| ① 动态检查 | 每生成完一个 Token，检查 Batch 内所有请求状态 | 发现已完成请求（`<EOS>` 或达到 `max_tokens`） |
| ② 踢出旧客 | 立刻把已完成请求的 KV 缓存移出，释放显存 | 请求 A 不再占用 GPU 算力 |
| ③ 迎接新客 | 把等待队列中的请求 B 的 KV 缓存加载进空位 | 请求 B 无需等当前批次结束，直接进入下一轮 |
| ④ 混合编队 | 新请求 B 与旧请求 C、D 拼成新 Batch | 每轮迭代 Batch 组成动态变化 |

### 7.1 为什么只有 vLLM 能做 Continuous Batching？（关键依赖）

因为 Continuous Batching 有一个极其苛刻的前提：显存必须支持“灵活且动态”地插入和删除请求。

- 传统框架（无分页）：每个请求的 KV 缓存必须占据连续的一大块显存。当你把请求 A 踢出去后，它留下的那块空间可能因为大小不匹配，导致新请求 B 塞不进去（外部碎片），最后还得重排内存，代价极大。

- vLLM（有 PagedAttention）：KV 缓存是按小块（Page/Block） 零散存放的。踢出请求 A 时，只是释放了几十个零散的小格子；插入请求 B 时，只需要找到任意空着的零散小格子填进去就行，无需连续空间。

> 结论：PagedAttention 是 Continuous Batching 的“地基”，Continuous Batching 是 vLLM 在“地基”上盖出的“摩天大楼”。 没有前者提供的零散分页能力，后者根本无法实现。


## 8. 我的选型
- 开发阶段：Ollama（简单、够用）
- 生产环境：vLLM（高并发、高吞吐）
- 后续升级路径：保留 Ollama 做本地开发，上线时切换 vLLM 部署

## 9. 面试怎么讲
> “Ollama 适合开发阶段，简单易用。但生产环境需要处理多用户并发，vLLM 的 PagedAttention 能把 K/V Cache 切成页面按需分配，配合 Continuous Batching 实现高吞吐。选型原则是：开发用 Ollama，生产用 vLLM。”
